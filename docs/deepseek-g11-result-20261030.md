## 3. Agent 实际查了什么

实际顺序：自动 inventory → 模型再次 inventory → 入口依赖探测 → 5678 端口 → localapp 进程 → downstream 进程 → 再查5678监听 → 再查 localapp 进程（内存排序）→ app.log → downstream 依赖探测 → **策略要求精确查5679监听** → **策略要求读独立 downstream.log**。

两项新增检查在真实运行中执行，参数分别为 `local_port=5679, listening_only=true` 及 `service=downstream, path=已登记日志, lines=100`。它们由共享确定性策略补查，原模型建议单独保留，不能算作假设保护或矛盾机制的贡献。

本场现场事实：

1. 入口 TCP 可连，HTTP 探测返回503；5678监听 PID21220/python.exe，不能由此认定应用逻辑正常。
2. app.log 两条本场日志均含 `upstream connection failed`。原文是日志行中的转义 JSON，不能把解码后拼出的片段当作原始连续引文。
3. downstream 的127.0.0.1:5679 TCP连接被拒；精确监听快照为空，匹配数0。
4. downstream 配置进程快照为空、匹配数0、跳过数0。inventory 已表明存在精确进程身份配置，模型将其泛称为“只按进程名匹配”不准确。
5. downstream.log 读取成功但0行。inventory 标明对象为 `kind=process`、`service_name=null`、事件通道未配置。

这些材料足以描述已观测故障层，但不能证明 downstream 为何不存在监听/进程，也不能仅据空日志排除异常。未启动、崩溃、未部署仍需历史因果材料。本场允许日志没有记录原因，Windows事件通道也未配置；不能把这些实际限制扩写为所有检查已经穷尽。

## 4. 审核发现

### 4.1 引用校验有效阻拦了不连续原文，但模型仍不会稳定引用

最终模型提议共有8组不同的“证据ID＋引文”，5组可连续匹配、3组失败：

| 证据 | 失败原因 |
| --- | --- |
| `ev-bfeb516a541548ff89ae1c743210297a`，app.log | 模型采用解码后的裸 JSON 片段；原payload保存的是转义日志行 |
| `ev-921686d9a8da49aaa5d4e4e8f7132c47`，下游探测 | 引文跳过 port 和 tcp 之间的 dns 字段，将不相邻字段拼接 |
| `ev-403f1e8e19de4e509fbfba5649b9b35c`，下游进程 | 跳过 sort_by、selection 等中间字段 |

最终结构化 diagnosis 保存4条已匹配引用，报告还打印了另一个替代解释中的有效引用。机械审核 `quotes_observed=true` 核对的是过滤后的结构化引用，**不能推导全部模型引用或全部报告语义正确**。六轮共48次引用出现、其中23次未匹配，包含重复引用，不能当48个独立样本。逐项记录见 `offline-audit.json`。

本轮保留严格原文门槛，没有为得到通过结果放宽匹配。后续优先考虑模型引用已有证据片段标识，由程序从账本回取原文，同时继续验证候选条件和语义支持；不能只靠改提示词宣称已解决。

### 4.2 候选文字、结构化条件和保护/改向目标不一致

- “localapp进程未运行或未监听”候选却带 `listening=true` 条件。已有监听支持该条件，却反驳候选文字。程序检查了谓词，未证明自然语言解释与谓词同义。
- 领先入口候选预期 HTTP200，被503反驳后，矛盾机制选择了上述候选，改去再次检查5678/localapp，而当时模型原本提议读入口日志和查下游。
- 下游候选后续仍保存 `tcp=ok` 的必要预期，文字却描述依赖不可达；沿同一ID的预期更新受身份保持规则约束，不能由模型随意改写成已经符合现场的新条件。这不等于文字与条件已经一致。
- 机械轨迹：保护机会1次、保护额外改查0次；矛盾机会1次、实际改查1次；保护到期1次。机械行为检查通过，候选正确性仍待语义审核。本场改向包含重复检查，不能宣传收益，也不能用这一场证明机制整体有害。

### 4.3 已确认并免费修复的两处程序错误

1. `_mapped_dependency_check` 原来直接比较日志路径字符串。配置返回 `D:/.../downstream.log`，Probe 返回 `D:\...\downstream.log`，同一文件被判为未读。第5轮读取后，第6轮策略再次选中同一日志，随后因计划文本已完成而停止。
2. 停止分支没有说明“所选计划已执行”，默认归因为“模型未提出下一项检查”。实际上模型明确提出服务/事件检查，被重复日志补查覆盖。停止归因错误，不是模型没有方案。

修复范围仅为共享策略：用标准库 `ntpath` 做 Windows 词法规范化；保留服务身份和不同文件的区分，不解析符号链接、不改变路径权限。缺少或非字符串路径不当成已读取。重复计划停止时将真实原因同步到记忆与报告，保留“未独立验证穷尽”的限制。

先反例后修复：18项定向检查中12失败、6通过；包括8项跨斜杠/大小写的四组案例和4项停止理由案例。修后相关回归通过，最终结果见第6节。用**同一真实记录的输入**分别调用运行快照与修后策略，前者重选已执行日志、后者不重选；这是离线核对，没有重采现场或调用模型。

修复并不证明后续服务/事件提议可执行：本场对象是进程、未登记Windows服务，事件通道未配置，仍应给出具体限制。不会据修复后的新分支回写原场成绩。

### 4.4 尚待修复的报告/证据边界

停止裁决使用 `observed_faults and not decision.contradictions`，把模型自由文字“矛盾”用作整个故障层报告的否决条件。本场两条文字实际在说明空日志/进程匹配的证据限制；与此同时，共享观测规则独立识别了入口503、下游TCP失败、无监听和未发现配置进程。该门槛使它们一并降成 `unlocated`，并不给具体人工建议。

本轮**没有修改此门槛**。下一步应区分“现场事实相互冲突”“候选预期被反驳”“深层原因缺证据”，为每种情形增加反例，保留已验证事实同时限制未知因果。不能简单删除全部矛盾检查来提升本场分数。

报告的部分候选“尚未执行”说明依据自然语言步骤名称匹配，已有 app.log 等价工具调用仍可能被误写为未执行。下一步也需按具体对象、操作、参数和执行结果关联，避免用文案差异充当采集阻碍。
