## 原因和边界

1. **主要断点是输出契约没有闭合。** 末轮有检查意图、对象与合法参数，但字段没交齐。当前schema允许这些字段缺省为空，业务守卫才拒绝；提示词写“必填”并没有保证生成可执行计划。`next_question_id` 只是关联已有问题，不会补成完整检查。不能简单断定是模型不理解故障，更不能通过放宽守卫或猜填参数解决。
2. **保存的不完整候选不能接住这次提议。** edge候选从首轮起就缺鉴别问题与预期观察，后续反馈已明确不可调度。末轮即使引用旧问题，仍没有完整、合法的保存检查可继续。工具已加载、来源已配置、路径在白名单，而且本轮从未读过edge日志；此处不是没有采集工具或场景没有日志。
3. **自然解释与结构化证据支持仍有落差。** 四轮解析前函数参数均省略 `supporting_evidence`，模型在文字里使用了日志，但没有完整交付可核验的引用支持。有限条件只验证现场谓词，不能证明停止发起者或完整传播因果。后续应把“带引用、按来源陈述的解释”与“确认根因”分开，而不是自动把自然文字升级为根因。
4. **报告保留事实，解释仍过泛。** 报告保留了停止记录、连接失败、无监听及应用报错，但主解释仍为“当前异常，启动、退出及传播原因未确认”。这是已观察到的收束限制；上游引用缺口与渲染各贡献多少，仍需用保存输入离线核对，不能先把它全归为报告模块问题。

还有初始inventory重复一次；全量端口快照与后来精确端口检查部分重叠，但后者参数和目的不同，不一概算无效重复。请求712耗时约45秒后成功，没有按失败处理。已知预算异常终止审计问题本次未触发，未修；上场停止范围解释问题也未改。
