# 替代候选全空：向内一层的逻辑原因

结论：当前最直接的断点在“自然语言竞争解释 → 独立候选及其可区分预期”的表达链。旧故障场景真实且可区分，也在模型文字中诱发过多个解释；但运行契约接受把这些解释合并为一个主假设，机制随后只跟踪其中一个有限条件。场景快速收敛、共用调度与身份冲突进一步压缩机制空间。现有证据不足以把唯一原因归给场景或模型能力。

本次仅分析已有材料，没有实现候选修复、调用模型、执行现场工具或扩大实验。八场原报告、评分、输入与轨迹均未回写。可复核摘录及原文件哈希见 `runtime/competing-hypothesis-preflight-20261104/candidate-representation-cause-audit.json`。

## 现象在什么位置已经出现

本次读取八场的38份 `behavior_context.model_suggestion`，以及44份实际发送的 `InvestigationDecision` HTTP请求输入（包含纠正请求，不能当作44轮独立调查）。38份提议的 `alternatives` 全部为空。

`decide_from_evidence` 在复制决策后、应用业务校验和机制之前保存 `model_suggestion`。所以这38份空列表已经存在于业务守卫之前，不是身份守卫或机制调度删掉了替代候选。

但 `model_suggestion` 已经过结构化解析，不是供应商原始响应。运行器只保存HTTP请求、响应元数据及usage，未保存响应正文；`alternatives` 的Pydantic默认值又是空列表。因此无法追溯区分“原响应省略该字段”与“显式返回空列表”。结构化代码对非空合法列表没有静默过滤逻辑；仍不能声称逐字审计过原始输出，也不能据空列表断言模型脑中没有竞争解释。

## 已确认的表达断层

下游G01首轮提议写道：

> localapp 入口不可用可能源于应用进程未运行或未监听 11139 端口，也可能源于下游 downstream 依赖不可达或应用内部错误；需先探测入口与依赖连通性。

同一提议的 `expected_observation` 还区分了“TCP失败/未监听”与“入口TCP成功但HTTP报错、downstream失败”。然而 `alternatives=[]`、`hypothesis_condition=null`。这说明场景已经提供了可想到的竞争方向，分支也出现在文字中，但没有交成可分别保存、遗漏、反驳和调度的对象。

沿实际请求追查，44份工具schema都只有 `hypothesis` 必填；`alternatives` 没有非空约束，描述为“结论前必须列出实际核验的替代解释及证据；healthy不能留空”。系统提示要求给可检查的替代解释填check，用户输入也要求保留候选，但没有把“主假设只能表达一个解释、调查途中已有竞争方向须分别登记”建立为一致的输出语义。结论审核的字段同时承担调查中候选管理，含义存在错位。

这些事实证明：合并主假设和空列表是契约允许、现有输出反复采用的路径。它们支持“契约未把文字分支转成独立候选”的解释；尚未通过控制实验证明某一句提示或默认值是模型这样输出的唯一原因。不能直接归因于模型弱，也不能靠强制每轮造两个候选解决。

## 机制真正跟踪的是什么

`mechanism_candidate` 把合法condition转成有限条件公式；候选身份由该公式和condition参与确定。机制不理解自然语言中的因果分支。这是保护证据边界的既有设计，同时限定了机制实际能力。

下游G01第二轮自然语言仍是“应用内部或下游依赖”，文字预期能按downstream探测正常/失败区分两者，结构化condition却是 `dependency_probe/localapp: http.status == 503`。持续的503对这两种解释都成立，无法区分它们；下游故障的新证据也不会反驳入口503。机制可以验证这个条件，但验证不到文字里的竞争关系。

下游G11又展示了这个错位的后果：第一轮旧ID绑定入口HTTP503，第二轮模型沿用该ID、改成下游TCP失败。身份守卫因此拒绝，保存的条件仍为入口503，随后由共用监听补查继续。9轮下游身份冲突都发生在候选已经空缺之后，不能解释首轮为何没有alternatives；它们会妨碍后续候选演进。

因此当前实现更准确地说是在保护和反驳“有限现场条件候选”。只有自然解释各自有不同、合法且有用的条件和未完成检查时，才可能体现为假设调查的收益。把不同解释都绑定到同一503，或让一个候选承载多种解释，都削弱了这个前提。新加稳定edge代理也不会自动解决同一表达问题。

## 场景和调度分别承担多少责任

| 因素 | 已有证据 | 可以下的判断 |
|---|---|---|
| 场景是否没有竞争解释 | 多个真实首轮提议已列进程/监听、下游和内部错误，并在文字预期中区分结果 | 不能把空候选归结为场景完全没有歧义 |
| 场景是否容易快速收敛 | 配置错误四场仅2—4个保存决策轮；一次计划可同时取日志、配置、进程和依赖证据 | 适合基本诊断，对跨轮保留和检查取舍的辨别力不足 |
| 条件是否覆盖关键原因 | 条件支持TCP、HTTP、监听、进程和服务状态；不支持配置字段或日志语义 | 配置场的关键区分能写进报告，不能直接参与这套条件机制 |
| 共用调度是否覆盖作用 | 下游四场共12轮共用补查，其中9轮身份拒绝 | 会减少增量调度空间，但不能倒推成候选最初为空的原因 |
| 首轮决策是否处于同一取证时点 | 2/8场首次决策前已有入口HTTP503，其余只有inventory；均出自各自自主执行轨迹 | 首轮反证机会不能只按组名比较；不是机制开关效应或答案泄漏的证据 |

没有误导线索或需要跨轮保留的检查取舍，也不表示业务夹具无效。实验需要的是机会与收益可以被观察，不应故意制造错误模型、削弱关闭组或强迫无意义串行检查来获取正结果。

## 这一层分析后的优先级

先修正候选契约的语义：让确实提出的不同解释各自携带身份、可区分的有限预期和具体检查；允许没有合理替代解释时为空，允许暂时不能表达的解释保留未知。已知入口503可以是事实，不应替代下游与内部错误各自的鉴别预期。保留当前身份、范围和证据守卫，不把程序拆自然语言当作模型自主候选。

免费回归只能证明这种输入能被保留、按证据更新、正确调用既有调度，不能证明模型会自然产生它。只有输出语义先明确，最小模型观察才有清楚的判据：是否形成独立竞争候选，后续是否仍有合法未完成检查，以及机制选择是否有真实增量。若候选已经自然形成但检查当轮全完成，才优先判断场景对机制辨别力不足；若仍合并叙述，则继续定位生成/契约问题，不扩大场数。
