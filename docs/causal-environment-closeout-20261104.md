# 能区分原因的测试环境：免费收尾

2026-11-04。本阶段完成审计修复、日志路径契约与必要参数投影修复，并建立正式 Probe 链路可读取的两原因对照环境。最终相关回归 **686 passed**，两轮正式链路预检通过，**新增真实模型请求为0**。这证明测试环境具备检验条件，不证明模型自主找根因已经通过。

## 本次查清的原因

上一场不是单纯“日志工具不足”或“报告排版不好”。保存轨迹暴露了两个工程问题：

1. 第3轮先排查此前保存的候选，记录 `no_eligible_saved_candidate`，随后从本轮新候选中找到合法检查并实际执行。审计把中间排查结果当成最终停止，要求计划为空，造成误判。现在按原顺序重建旧候选排查与本轮候选选择，并核对具体参数和实际执行；成功延续时清除中间停止理由。身份、范围、重复查询和失败守卫保持原有要求。
2. 文本日志工具需要实际白名单路径，业务目录的 `log_refs=['localapp']` 是服务引用。进一步核对真实 HTTP 输入发现：请求673、674仍含 `localapp.log` 实际路径，675—680已经没有该路径，而 `log_refs` 仍在。原因是最近8份原文的投影会挤掉早先 inventory；不能仅要求模型遵守一个后续已不可见的参数契约。现在单独投影仍有效 inventory 中的精简日志路径表及来源 evidence ID，只保留本次允许服务。完整历史、原文数量上限、工具权限及公开接口不变。过期、截断、错误、其他目标的 inventory 不进入新投影；模型别名与相邻未授权路径仍拒绝。

以上是可定位的贡献因素，不据此断言它们足以解释全部调查不足。自由文本因果判断的验证边界未改，也未把引用日志自动升级为 `confirmed_cause`。

## 什么环境才足以做下一次检验

至少需要：真实触发故障；相同入口症状对应不同原因；允许工具能取得区别原因的证据；证据有当前时间窗和对象身份；控制器答案不进入模型输入；清理与恢复可独立检查。验收深度限定为解释本轮停止或启动失败，不要求查明未知操作者。

本次复用 edge → localapp → downstream 三进程拓扑：

| 项目 | 停止请求场 | 绑定失败场 |
|---|---|---|
| 注入方式，仅控制器掌握 | 请求应用按已有 stop-file 机制退出 | 独占绑定真实端口但不监听，再启动应用 |
| edge 表象 | HTTP503，temporarily unavailable | HTTP503，相同响应体 |
| downstream 现场 | TCP失败、无监听、配置身份进程不存在 | 同左 |
| 应用自己写出的区别证据 | shutdown_requested、controlled_stop、UTC、PID、initiator=unknown | bind_failed、实际 errno、失败端口、UTC、PID |
| 进程结果 | 正常退出 | 启动非零退出 |
| 原因边界 | 应用记录了停止请求，发起者仍未知 | 应用记录了该端口绑定失败，不声称查明占用者 |

绑定失败不是控制器伪造日志。新增字段仅为共享夹具现有绑定失败日志补 UTC 时间，供原有观测窗口校验。Windows 启动器和 Python worker 的 PID 在退出前由独立进程树采集；不会用日志自己的 PID 证明其来源。非预期错误、错误端口、未知错误码、正常退出或无法独立匹配的 PID 均不能算注入成功。
