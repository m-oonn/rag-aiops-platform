# 接口响应变慢与超时分层排查

作者：本项目编写。版本：2026-10-23。适用：Windows 本机专用测试业务。
本文依据公开文档编写，作为调查参考。具体超时阈值应以本次配置为准，不提供预写故障答案。
参考：https://learn.microsoft.com/en-us/powershell/module/microsoft.powershell.utility/measure-command
参考：https://docs.python.org/3/library/socket.html

## 1. 先测量再判断

接口响应变慢是现象，不等于 CPU 过高或数据库故障。记录接口路径、测量时间、状态与总耗时。
只对专用业务采用有边界的请求：curl.exe --max-time 5 -s -o NUL -w "%{http_code} %{time_total}" <允许的URL>。
这里五秒是本机测试示例，不是通用生产阈值。超时错误和 HTTP 错误需分别记录。
正常对照应使用相同路径、相同请求条件；单次测量不能代表持续性能或所有用户体验。
测量可用 Measure-Command 包围只读请求，注意命令总耗时还包含客户端开销。

## 2. 用分层观察鉴别

依次核查入口耗时、应用日志中的请求耗时、下游健康与建连结果、允许采集的 CPU 和内存趋势。
下游可连接只证明建连阶段，不能排除处理慢；需要区分连接耗时与业务响应耗时。
应用日志若显示等待下游，应核对同一时段的下游响应；若下游正常而应用慢，继续检查应用内部等待。
一次 CPU 快照偏高不足以解释具体请求，需要时间关联及其他证据；低 CPU 也不能排除锁等待或阻塞。
日志不可用时保留应用等待、依赖变慢等合理候选，再选择能区分它们的检查，不因早期缺证据就强行排除。
不填满磁盘、不压力轰炸真实服务。修复由人操作，恢复后用同一路径的有界请求再次测量。

结论边界：小型本机排查只能解释已检查时间与范围；缺少阶段耗时信息时应诚实保留未定位原因。
