# 应用异常与 HTTP 5xx 排查

作者：本项目编写。版本：2026-10-23。适用：Windows 本机专用 HTTP 业务。
本文是项目排查手册，不是厂商原文；不得把手册描述当成本轮发生了某种异常的证据。
参考：https://www.rfc-editor.org/rfc/rfc9110.html
参考：https://docs.python.org/3/library/traceback.html

## 1. 先区分入口错误和依赖错误

HTTP 500 表示服务遭遇意外情况而无法完成请求；HTTP 503 表示当前无法处理请求。
状态码本身没有唯一根因。同一种 5xx 可以来自应用异常、下游失败、网关或受控错误模式。
记录发生时间、请求路径、状态码和可脱敏的响应摘要，使用相同路径再次检查。
检查应用进程与监听端口，确认请求是否真正到达该业务，而不是其他占用端口的进程。
使用应用日志核对同一请求时间窗口，查找 traceback、异常类型及调用位置。

## 2. 根据反证改变下一检查

若先怀疑下游不可达，后续 TCP 和下游健康请求均成功，这些观察反驳的是“该检查时刻下游不可连接”。
它们不能排除较早的瞬时失败、认证异常或另一个实际配置地址，需要用入口日志继续鉴别。
入口日志若明确记录应用内部异常，而下游检查正常，应优先核查异常栈对应的应用代码或配置。
保留异常类型、位置、时间与请求关联；避免把其他时间的旧 traceback 作为本次原因。
没有日志权限、日志为空或只看到通用 500 时，报告应写“应用层异常待核实”，不能编造异常名。
由人修复专用测试业务的受控异常或配置，恢复后重复同一接口、下游检查，并确认没有新增异常日志。

结论边界：定位到应用错误与定位到具体代码缺陷不同；只有当前请求的可靠异常证据才能支持后者。
