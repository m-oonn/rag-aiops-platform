## 一场真实自主验证

控制器以 stop-file 请求停止 downstream，不把隐藏故障答案放入 Agent 输入。业务日志记下请求事件和 worker PID，PID 属于 downstream 启动进程族；随后进程正常退出，Agent 观察到 downstream 进程匹配数为0、端口无监听、TCP拒绝，localapp/edge均返回503。Agent 的日志工具读取到事件，后续决策上下文含事件原文与 evidence ID；不是“工具读不到日志”。

真实模型在 step 3 提出“downstream 已不在运行”，引用 `shutdown_requested/controlled_stop` 日志，并提出查询事件通道以追查发起者。该日志只能证明应用记录了停止请求；它的 `initiator=unknown`，不能证明真实操作者，也不能单独证明停止请求与进程退出的因果关系。最终报告仍将启动、退出及异常传播原因列为未知，没有确认根因。因此可确认模型使用了业务退出线索，但未形成可审核的深层根因判断。

轨迹另暴露候选路径问题：模型随后提出 `path=localapp` 等配置别名，当前文本日志参数守卫要求实际路径匹配显式白名单，故候选被拒绝。系统沿保存检查读取 downstream 日志和其他合法检查，重复检查守卫有效；模型再提出的 localapp 检查仍有非法路径，最终停止。该行为说明当前工具接口的别名契约没有被模型稳定遵守，不能归为“日志工具无法工作”。

## 结论与下一步

此阶段回答了采集链路问题：现有日志工具和 Probe 链路足以读取、传递应用记录的停止请求，不需要新增日志工具或系统审计服务。场景可区分“直接终止、无业务退出记录”和“受控停止、有业务退出记录”，但后者只是夹具的受控停止请求，不是崩溃或生产服务管理器的证据。

本轮没有证明 Agent 能从任意现场自主找到任意深层根因：模型确实使用了停止线索，但报告仍保留因果未知，且模型曾生成不符合日志路径契约的候选。真实整场又被审计不一致判失败。下一步应先用保存轨迹定位并修复审计重建分歧，再用构造输入确认模型可用的日志参数究竟是别名还是路径、守卫和提示是否一致。两项免费门槛通过后，再单独判断是否值得授权新的一场自主模型验证。此记录不是对本次失败的重审或改判。
