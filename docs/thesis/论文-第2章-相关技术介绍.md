# 二、相关技术介绍

> 工作稿说明：本章对应导师版开题报告写作提纲第二章，只介绍技术背景与本文的取用范围，不涉及本文自身设计（留第三章）与实验（留第五章）。文末编号 [n] 对应开题报告"主要参考文献"顺序；引用只到**题名与书目层面可核对**，未逐篇全文审读，核对状态见《参考文献对照-导师版36条.md》。凡标"工程观察"的句子来自本项目源码与运行记录，不属文献引用。

本章介绍四个方面的技术基础：大模型工具调用、检索增强生成与向量检索、基于状态图的流程编排，以及故障诊断中的候选原因与证据处理。四者分别对应本文系统"怎么调工具""从哪里获得经验""怎么组织多轮检查""怎么判断并收住结论"，是第三章需求与设计的技术前提。

## （一）大模型工具调用技术

### 1. 从文本生成到工具调用

大语言模型最初的使用方式是"输入文本、输出文本"，模型自身不接触被诊断系统的运行状态。工具调用改变了这一点：模型在生成过程中选择一个外部函数并给出参数，系统执行后把结构化结果回填给模型，模型再据此决定下一步。ReAct[21] 把这一过程明确为"推理—行动—观察"的交替循环，即模型每轮先写出当前判断，再选择一个动作，用观测结果修正下一轮判断；Reflexion[22] 进一步引入跨试验的语言化反思，让智能体把失败经验写成文字留给下一轮，而不更新模型参数。

对于运维诊断，这一形态的价值在于把"模型的知识"与"现场的事实"分开：模型负责提出"下一步该查什么"，工具负责回答"实际是什么"。RCAgent[24] 与 RCACopilot[25] 都是沿这个思路，把日志、指标、代码检索等能力封装成工具交给大模型调度，用工具返回替代模型臆测。Xpert[26] 从另一个角度使用大模型，用历史工单生成查询建议以降低人工排障的检索成本；[27] 则从"让模型听取专家"的角度讨论操作系统故障诊断，强调专家经验应进入诊断流程而不是被模型先验替代。综述[28] 系统整理了这类"大模型智能体 + 工具"在根因分析中的做法与边界。

本文取用其中最基本的形态：**单智能体的循环式工具调用**，即由模型生成检查计划、逐个执行、根据结果再计划；不采用多智能体分工，也不采用让模型凭记忆直接给结论的做法（第三章 FR-05 至 FR-08）。

### 2. 工具接口的解耦：模型上下文协议

工具数量增长后，耦合方式会成为主要问题。若每个工具都以函数形式写在主服务进程内，会带来三个后果：工具崩溃会带走主流程；工具依赖的重型客户端必须与主服务同环境；更换某个后端（例如把模拟监控换成真实监控）需要改主服务。

模型上下文协议（Model Context Protocol，MCP）把工具访问抽象成客户端/服务端关系：工具提供方以独立进程或独立服务暴露"有哪些工具、每个工具的参数与返回结构"，调用方作为客户端按协议发现并调用。这样工具实现与调用方可以分别演进，权限与网络边界也能画在两者之间。

工程观察（本项目）：诊断侧的查询工具被拆成 7 个独立进程，分别承担监控指标、日志检索、知识库检索、变更记录、诊断收集、受控终端与探针网关；主服务只作为 MCP 客户端。这一拆分不是为了性能，而是为了让"某个工具不可用"成为一个**可表达的正常状态**，而不是主流程的异常——这一点直接来自开题报告技术路线中"工具正常与部分不可用"的对照要求。

### 3. 工具调用的可靠性问题

工具调用在工程上会以多种方式失败：连接被拒绝、请求超时、返回空结果、返回结构与约定不符、同一结果被重复调用。这些失败与"服务正常"在现象上可能相同（例如"没查到错误日志"既可能是没有错误，也可能是日志服务不可用），若不显式区分，模型很容易把"查不到"当成"没问题"。

常见的处理策略有三类：重试（对瞬时故障）、降级（换用备用数据源）、显式未知（记录缺失并把不确定性传给结论）。三者的选择取决于该证据在结论中的地位，而不是取决于实现方便。开题报告在证据工具模块中提出的两条要求——"单独记录缺失信息并利用其余可用工具继续排查""避免将查询失败误判为服务运行正常，也避免重复使用同一结果来提高判断的可信度"——正是这一区分在需求层面的表述，本文在第三章 FR-17、FR-18 与第五章的工具不可用实验中落实。

## （二）检索增强生成与向量检索

### 1. 检索增强生成的基本流程

检索增强生成（RAG）[23] 在生成前先从外部语料中检索相关片段，把片段作为上下文交给模型，使答案建立在可追溯的资料上而不是模型的参数记忆上。典型流程为：语料分块 → 建立索引 → 按查询检索 → 与查询一起拼成上下文 → 生成并附出处。

对本文而言，RAG 的作用不是"让模型更博学"，而是提供**排查经验**：故障现象相似时，历史案例与排查手册能提示"这类现象通常先查什么"。这里必须保留一条边界：历史案例证明的是"以前遇到过类似情况"，不证明"这次也是同样的原因"；当前故障是否成立，仍须由本次运行数据回答。开题报告在知识库与经验检索模块中明确写了这一点，它是本文结论边界的组成部分，而不是实现细节。

### 2. 稠密检索与稀疏检索

稠密检索把查询与文档片段分别编码为定长向量，按向量相似度排序。它的优势是语义匹配——问"接口很慢"能召回写着"响应时延升高"的段落；代价是依赖嵌入模型，且对专有名词、端口号、错误码这类精确串不敏感。

稀疏检索以 BM25 为代表，按词频、逆文档频率与长度归一化打分。它对精确词匹配可靠、无需训练、可解释，但对同义改写无能为力。两类检索的互补性使混合检索成为常见选择。

向量检索需要向量数据库支撑。Milvus 提供向量集合的存储与相似检索，支持按标量字段过滤，适合"分库检索"这类带条件的场景。工程观察：本项目的向量集合按 1024 维嵌入建立，检索时可按知识库标识过滤。

### 3. 融合与重排

把两路检索结果合并的常用做法是倒数秩融合（Reciprocal Rank Fusion，RRF）：对每个结果取其排名 rank，得分为 1/(k+rank) 之和，k 通常取 60。RRF 只用排名不用原始分数，因此不必把两类不可比的分数校准到同一量纲，这是它被广泛采用的原因。

融合之后通常再加一层重排：用一个交叉编码模型对"查询—片段"成对打分，取前若干条进入上下文。重排能显著提升精度，但引入外部服务依赖，因此必须有失败回落路径（重排不可用时按原顺序取前若干条）。工程观察：本项目的检索链路为"混合检索（RRF，k=60）→ 重排 → 取前 5 条"，分块长度 1000、重叠 200，初检条数在启用重排时取 2 倍；回答要求逐段标注来源编号，便于读者回查。

### 4. 本文取用的范围

本文使用 RAG 只解决"经验从哪里来"，不把检索结果当作故障证据；检索片段带出处进入上下文，报告中也区分"运行数据"与"历史资料"（第三章 FR-20）。检索质量、切片对语义的破坏、重排服务不可用时的回落效果，属第五章测试范围，本章不预设结论。

## （三）基于状态图的流程编排

### 1. 线性链的不足

单次问答可以用"检索—拼接—生成"的线性链完成；多轮诊断不行。原因有三：检查项的数量在开始时并不知道，取决于每轮结果；某轮结果可能推翻前一阶段的计划；系统需要在轮次之间保留已收集的证据、已排除的候选与未解决的问题。

把这类过程写成固定流程会让代码承担本应由模型承担的判断，而完全交给模型自由对话又会丢掉可控性（轮数、工具权限、结论边界都无从约束）。折中方案是把"可由程序保证的部分"放进图结构，把"需要判断的部分"留给模型：图负责顺序、分支、状态累积与终止条件，模型负责在节点内生成计划与解释结果。

### 2. 状态图的基本机制

基于状态图的编排框架（以 LangGraph 为代表）提供以下要素：状态（一个带类型声明的字典）、节点（读取状态、返回状态增量的函数）、边（固定顺序与条件分支）、归约器（声明某字段是覆盖还是追加）、编译（得到可执行图）、检查点（每步保存状态快照，可按线程标识恢复）。

两个机制对本文特别重要。其一是**追加式状态**：工具结果以追加方式写入历史，使"做过哪些检查、各自返回什么"始终可回溯，而不被后续结果覆盖。其二是**检查点**：每步落盘后，进程重启或人工介入都能从最近状态继续，而不必从头重跑。

### 3. 本文使用编排的方式

本文的编排是"计划—执行—再计划"三段循环：计划节点把用户问题拆成有序检查项；执行节点每次取一项、调用工具、把结果写入状态；再计划节点根据新结果决定"继续、改变计划、还是收束给结论"。开题报告为此规定了三个结束条件——证据足以支持结论、没有可继续的检查项、达到调用次数上限——三者分别对应"模型判定收束""计划耗尽""程序兜底"，其中最后一条由程序保证，不依赖模型自律。

工程观察：本项目用一张状态图承载上述循环，节点为计划、执行、再计划（在开启人工复核时另有复核节点），状态字段区分"计划""已执行步骤""原始工具返回"与"最终回答"；计划与步骤采用追加语义，检查点同时写内存与本地数据库，以便挂起后恢复。另有一处工程细节值得记录：追加语义依赖归约器声明，若状态模块使用延迟注解（`from __future__ import annotations`）把类型声明字符串化，编排框架将读不到归约器，追加会静默退化为覆盖——这类"静默退化"比报错更危险，是本文在实现中专门加注释禁止的写法。

### 4. 与既有编排思路的关系

"先规划再执行"（Plan-and-Solve 一类提示）能减少逐步试探的随机性，但计划一次生成后若环境反馈与预期不符，缺少修订环节。本文保留计划的前提价值，同时把"再计划"作为独立节点，使计划可以被新证据改写；这与 ReAct[21] 的交替循环同源，区别在于把"行动"限制在预定义工具集合内，并对终止条件加了程序侧约束。

## （四）故障诊断中的候选原因与证据

### 1. 诊断的经典框架

基于模型的诊断把"什么可能坏了"表示为候选集合，用与观测冲突的假设逐一排除，其经典形式是 de Kleer 与 Williams 提出的多故障诊断与冲突集[29]。决策论排障[30] 补上"下一步查什么"这一环：把每次检查看成有代价的信息获取动作，按期望收益选择下一个检查，而不是按固定顺序穷举。

这两个框架给本文两点启发。第一，诊断的对象是**候选原因的集合**而非单个猜测，系统应能同时持有多个候选并分别记录其状态。第二，检查顺序本身是一个决策，应当显式记录"为什么下一步查这个"，否则即使结论正确也无法审计。

需要说明的是，[30] 的完整形式依赖故障先验概率与检查代价的量化，本文没有采用这一量化路线：既没有可靠的先验分布，也没有把"检查代价"标定成可比数值。本文只借用其思想（候选并存、检查有目的），不宣称实现了决策论排障（第五章局限中重申）。

### 2. 微服务场景下的证据来源

微服务系统的故障定位研究已形成以观测数据分类的格局。日志方向的综述见 [5][6][7]，具体方法从日志序列异常检测 DeepLog[8]、模板与语义结合的无监督检测 LogAnomaly[9]，到面向日志本身不稳定性的 LogRobust[10]；指标方向有基于服务依赖图的 MicroRCA[11] 与基于扩展谱分析的 MicroRank[12]；调用链方向有基于 trace 的多维定位[17] 与基于控制流分析的性能建模[18]；多源融合方向有 Eadro[14]、Nezha[15]、HeMiRCA[16]；依赖关系与影响图方向有服务依赖发现综述[13] 与基于多层次影响图的定位方法[19]；变更视角有面向大规模在线系统的根因变更识别[20]。整体格局见 AIOps 综述[1][2]、异常检测与根因分析综述[3][4]。

这些工作大多以"给定完整遥测数据、离线训练模型、输出根因排序"为前提。本文所处条件不同：只有一个 3 至 5 个服务的小型测试环境，工具可能部分不可用，且要求系统在缺少某项数据时说明缺什么而不是猜。因此本文不实现上述检测模型，而是把它们产出的指标、日志、调用链当作**可查询的证据源**，由智能体按需查询——即把"检测精度"问题换成"证据获取与结论边界"问题。

### 3. 大模型智能体做根因分析的现状

在工具增强路线之外，近期工作开始关注智能体自身的推理结构：RCAgent[24] 与 RCACopilot[25] 展示了工具调用式排障的可行性；LATS-RCA[31] 把语言智能体的树搜索用于根因分析，用搜索代替单线试探；Hypothesize-then-verify[32] 提出"先假设、再验证"的路径并讨论并行化。综述[28] 对这条线做了归纳。

这组工作与本文的关系是"同问题、不同侧重"：它们关注如何让智能体搜得更准、更快；本文关注在证据有限且工具可能缺失的条件下，系统如何**不把不确定说成确定**。因此本文的机制重心在候选状态的维护、检查的触发条件与结论的定级，而不在搜索策略本身。

### 4. 不确定性与诚实性

大模型在证据不足时倾向于给出看似完整的答案，这类现象在幻觉综述[33] 与幻觉检测综述[34] 中有系统讨论；模型能否准确表达自身置信度，已有实证评估[35]；在无法回答时选择弃答（abstention）的策略与评测，见综述[36]。

对诊断系统而言，"诚实"不是语气问题而是接口问题：结论必须带等级，等级必须由证据状态推出，且读者能看出缺了哪一项证据。这正是本文把结论分为"已确认原因""已定位但原因待核实""无法定位"三档、并把待核实项与所需补充检查一并输出的原因（第三章 FR-20 至 FR-23）。本文不给概率置信度：在没有可靠标定的条件下，给出数值置信度反而会制造虚假的精确性（第五章对此再作说明）。

## 本章小结

本章梳理了四类技术基础：工具调用（含协议化解耦与失败处理）、检索增强（含混合检索与重排）、状态图编排（含追加式状态与检查点）、以及经典诊断框架与微服务证据来源。同时明确了本文在各处的取用边界——用工具调用而不靠模型记忆、用检索提供经验而不当证据、用编排约束流程而不放任自由对话、用候选与证据定级而不给概率。这些边界构成第三章需求分析的前提。
