## 0. 研究问题（全文的锚）

绪论的每一个小节都必须回指同一个研究问题，不得中途换问。本研究的问题定义为：

> **RQ：在症状复杂、证据噪声大、且诊断所依赖的工具服务可能部分缺失的条件下，如何让基于大语言模型的诊断智能体既判得准，又说得清、不瞎猜、坏不掉？**

由此派生的三条判定标准（贯穿全文，1.1.2 首次出现、1.2.5 呼应、1.3 收口）：

| 标准 | 含义 | 对应难点 |
|---|---|---|
| **判得准** | 在"症状位置 ≠ 根因位置"时仍收敛到真实根因 | 难点 1 |
| **说得清 / 不瞎猜** | 结论可追溯；证据不足时如实声明而非伪装确定 | 难点 1 提供结构，难点 2 提供门控 |
| **坏不掉** | 单个工具服务不可用不致整条链路失效，且降级路径仍可信 | 难点 3 |

## 2. 全文逻辑主线

绪论必须构成一条**单向推导链**，任意两节之间不能出现断点或回头解释：

```
1.1.1 领域背景：微服务故障传播 → 人工排障三老毛病 → LLM 三阶段流程是条新路
      ↓ 但这个新路有失效情形：隐藏故障
1.1.2 研究意义：把模型直接接进去会暴露三个结构性缺陷 → 提出 RQ → 给出三条承诺
      ↓ 这三个缺陷不是本文独有，是现有研究的共同缺口
1.2.1 整体分析：AIOps 与 LLM Agent 两条线各自成熟，但结合后缺"候选原因管理 + 可信度约束"
      ↓ 这个共同缺口可拆为三个难点
1.2.2 难点1（假设管理与证据推理）→ 小结给出 1A / 1B / 1C
1.2.3 难点2（不确定性表达与诚实性）→ 小结给出 2A / 2B / 2C
1.2.4 难点3（链路鲁棒性与结论可审计性）→ 小结给出 3A / 3B / 3C
      ↓ 三难点不是并列，是递进依赖
1.2.5 分析总结：说明依赖关系及原因 → 定选型 1B → 2A → 3C（顺序不可换）
      ↓
1.3 研究目标：以 1B / 2A / 3C 依次解决三难点，最终回答 RQ，并给出量化目标
```

**衔接检查点**（四个"承上启下句"必须存在，缺一则逻辑断裂）：

| 位置 | 必须出现的过渡关系 |
|---|---|
| 1.1.1 末尾 | 从"普遍排障困境"收窄到"本文研究的失败情形：隐藏故障" |
| 1.1.2 末尾 | 从"三个缺陷"升华到 RQ + 三条承诺（可收敛 / 可审计 / 诚实） |
| 1.2.1 末 | 从"代表性研究的效果"转折到"它们共有的缺口"，并拆成三难点 |
| 1.2.5 末 | 从"依赖关系"落到"因此本文取 1B → 2A → 3C" |

## 3. 逐节写作指引

### 3.1 1.1 研究背景及意义

#### 1.1.1 研究背景

| 项 | 要求 |
|---|---|
| **本节任务** | 说明本研究所处的领域背景与现实驱动因素，并**收窄到本文具体研究对象** |
| **硬性约束** | **仅 1 个自然段**（不得拆段）；建议 330–400 字 |
| **必须回答的 3 问** | ①这个领域正在发生什么变化？②现实中的痛点是什么（要具体，不要"越来越复杂"这类空话）？③本文研究的是这条新路径上的哪一种**失效情形**？ |

**写作步骤（四步，按顺序落笔）**

1. **现象层**：微服务化后故障的形态变化——"一处出问题会引发一连串跨服务报错，真正成因被埋在连锁现象之下"。
2. **痛点层**：工程师的排障方式与三个老毛病——响应慢、质量不稳定、经验难沉淀。给出**领域综述的两条前提性局限**（依赖预设拓扑/指标集；难以处理未见过的故障组合）【文献 1】【文献 2】。
3. **转机层**：LLM 在推理与工具调用上能力增强 → 一个诊断智能体自行"规划—执行—再规划"，学术原型为 ReAct【文献 17】与 Plan-and-Solve【文献 18】。
4. **收窄层（最关键）**：本文研究的不是这条流程的成功情形，而是它的**失效情形——隐藏故障**（症状复杂、跨组件，真实根因却是单点问题：CPU 饱和 / 内存溢出 / 连接池耗尽 / 网络抖动）。**必须给出四类具体根因**，否则"隐藏故障"是个空词。

**素材出处**：`研究方案大纲.md` §1.1.1；文献编号见其附录 B。

**常见错误**

- ❌ 从"人工智能发展迅速、大模型能力强大"起笔 → 与本文问题无因果链。
- ❌ 把隐藏故障写成"复杂的故障" → 隐藏故障的定义恰恰是**根因简单、症状复杂**，写成"复杂"就把论点写反了。
- ❌ 只讲 LLM 的好处，不讲它在这类故障上的失效 → 1.1.2 会失去立足点。

**自检**：读完这段，读者能否说出"隐藏故障是症状复杂但根因简单的故障，四类典型根因是 X/Y/Z/W"？不能则需重写。

#### 1.1.2 研究意义

| 项 | 要求 |
|---|---|
| **本节任务** | 明确指出本研究要解决的**具体问题**及其**价值** |
| **硬性约束** | **仅 1 个自然段**；建议 400–480 字（若要压到 400 字以内，须撤掉缺陷层的文献引用，改由 1.2 承担） |
| **必须回答的 3 问** | ①把 LLM 直接接进诊断流程，会暴露哪三个**结构性**缺陷（不是"效果还不够好"这类程度问题）？②这三者的**共同后果**是什么？③本文的核心主张与三条承诺是什么？ |

**写作步骤（五步）**

1. **亮出 RQ**（一句话，用加粗固定下来）。
2. **三个结构性缺陷**，逐条给编号 (i)(ii)(iii)：不可审计 / 置信度不可靠 / 工程链路脆弱。
3. **每条缺陷必须挂两类证据之一**（缺一即空谈）：
   - 现象级证据（本项目实测）：停日志服务后 8 场景中 3 例虚报确定；修复前停一个服务即 8 个工具全废
   - 文献级证据：RCAgent 同样止于最终答案【文献 27】；模型校准失准【文献 30】；自愈系统经典问题【文献 38】
4. **共同后果收束**：结论不可追责、不可信任，环境稍一波动就干脆不出结论。
5. **核心主张 + 三条承诺**：不做"又一个能出结论的诊断系统"，而是把故障诊断**从一次黑箱文本生成改造成一个可审计的信念更新过程**；须兑现 **可收敛 / 可审计 / 诚实**。

**边界**：本节**只提出问题与主张，不展开方法**。三阶段编排、假设空间、log-odds 参数一律留给 1.2 与后续章。1.2.5 之前出现"旁开""保护期""门控"等机制名词即为越界。

**常见错误**

- ❌ 把"研究意义"写成"本文贡献列表" → 意义是**问题的价值**，不是**成果的清单**。
- ❌ 三条承诺写得含糊（"提高可靠性""增强可用性"）→ 必须写成可判定的短句：必须给答案 / 必须说清结论来源 / 证据不足必须如实说明。

**自检**：把三条承诺拿去逐条检查系统行为，能否明确判定"做到了/没做到"？不能则重写。

#### 1.2.1 整体分析（对问题本身的分析）

**任务**：说明该问题的**应用广泛性**与**研究价值**，逐条列出代表性研究（方法 + 效果），最后以**小结**指出这些研究仍存在的"该问题"，并归纳出 **3 个难点瓶颈**。

**三段式结构（不可合并）**

**(1) 应用广泛性与研究价值**

- 需求端：凡有线上业务的企业均面临"告警多、排障慢"。
- 方法端：需把指标、日志、调用链三类异构证据关联推断，天然是"证据不完整、结论靠推断"的问题。

- 收在**两个前提性局限**上：依赖预设拓扑/指标集；难以处理未出现过的故障组合。

**(2) 代表性研究：逐条给方法与效果**

**表格写作铁律**

- 效果栏**不得**写"效果良好""显著提升"等无参照表述；须给基准名、对比对象、量化幅度，或明确写"无公开量化评测"。
- 效果栏**必须**写清该方法的**结构性边界**（它做不到什么），这是为 (3) 的小结做铺垫。

**(3) 小结：指出"该问题"并归纳 3 个难点瓶颈**

落笔顺序：

1. 先肯定两条线各自成熟：AIOps 检测与定位有方法积累（研究 1~3）；LLM Agent 能做多步工具调用与推理（研究 4~7）。
2. 转折：但二者结合、用于隐藏故障时，**共同缺口 = 诊断过程缺乏对候选原因的显式管理，也缺乏对结论可信度的约束**。
3. 把一个缺口拆成 3 个难点，每个难点**必须配现象级证据**：

| 难点 | 名称 | 必须给出的现象 |
|---|---|---|
| 难点 1 | 假设管理与证据推理 | 两类可观测错误：**过早放弃简单假设**（"复杂症状 ⇒ 复杂根因"先验）、**被复杂症状带偏**（级联 ERROR 主导权重，链首根因被淹没） |
| 难点 2 | 不确定性表达与诚实性 | 停日志服务后 8 场景中 **3 例虚报确定**；且只比对 Top-1 的评估会把猜测计为正确，**掩盖**缺陷 |
| 难点 3 | 链路鲁棒性与结论可审计性 | 停**一个**服务即 **8 个工具全部不可用**；系统只给结论、不给推理轨迹 |

4. 末尾留一句"三者并非并列，而是递进依赖，详见 1.2.5"作为过渡。

|---|---|---|---|---|

> **三张表的统一排布规则**：一律按 **XA → XB → XC 自上而下**排列，与三个小结的编号顺序一致。注意本文所选方法在三难点中的位置不同（难点 1 取 B、难点 2 取 A、难点 3 取 C），**不要为了"把本文方案放最后"而打乱 A/B/C 顺序**——编号顺序与选型位置是两件事，评委按编号核对。
> 补充：**每张方法表都要在"方法"列首显式写出编号**（如"**2A** 证据充分性门控 + …"），否则读者无法把表与小结对应起来。

**每节必须回答的 3 问**：①**解决了什么问题**？②**针对什么现象**（要给可观测证据，不能只给抽象描述）？③**为什么另外两个方法不够**？

#### 1.2.5 分析总结

**任务**：针对 1.2.1 提出的"该问题"，**重点论述三难点之间的依赖性及其原因**，并说明本研究拟**依次**采用 1B、2A、3C 分别解决难点 1、2、3。

**六个板块，缺一不可**

| 板块 | 内容 | 写作要点 |
|---|---|---|
| **(1) 依赖关系及原因** | 难点 2 依赖难点 1；难点 3 依赖难点 1+2；顺序必为 1→2→3 | **必须给因果推理，不能只给结论**。原因写法定式见下 |
| **(2) 方法组合与机制参数** | 1B / 2A / 3C 各自的关键机制与参数 | 用表格；**每行参数须给出代码出处（`文件:行`）**，见 `研究方案大纲.md` 附录 A |
| **(3) 收敛判定与辅助机制** | 收敛门槛、跃迁触发、步数上限、证据裁判结构、日志严重级加权 | 只放与"能收敛、能可信"直接相关的项，不堆全景 |
| **(4) 核心抽象** | 命名为"**旁开式动态分类**（sidebar dynamic classification）"，并说明它不是端到端文本生成而是可审计的信念更新过程 | 给定义句 + 与"决策论排障"【文献 36】的异同各一句 |
| **(5) 载体与贡献的区分** | 三层表：知识底座（RAG）= 载体 / 诊断平台（三阶段编排）= 承载骨架 / 诊断机制 = **贡献所在** | 防"绪论读起来像系统说明书" |
| **(6) 与现有工作的差异** | 差异**不在接入更多工具或更大的系统**，而在把诊断显式建模为可审计的假设管理与信念更新 | 逐条对三组研究线给差异（搜索式推理 / 不确定性量化 / 可解释 AI） |

**依赖关系的原因——定式写法（三段，必须写足因果）**

> - **难点 2 依赖难点 1**。要判断"证据是否充分"，前提是先存在一个**"证据 → 候选假设"的映射结构**以及各候选假设的概率分布；只有先知道"哪些证据在支持或反对哪个根因"，才谈得上"针对某个根因的证据够不够"。若没有难点 1 提供的假设空间，"证据充分性"这一概念**无从度量**。**故必须先解决难点 1。**
> - **难点 3 依赖难点 1 与难点 2**。一方面，可审计性的核心材料——信念轨迹、证据与假设的对应关系、决策记录——**直接来自难点 1 的假设空间**；另一方面，鲁棒性设计中最关键的一环是"工具降级时结论仍要诚实"：若没有难点 2 的诚实性门控，系统在证据缺失时只会产出**语气更确定的错误结论**，即"降级"反而放大不可信。**故难点 3 必须建立在难点 1、2 之上。**
> - **顺序的必然性**：若颠倒顺序（例如先做鲁棒性、后做诚实性），将得到"在证据缺失时稳定地输出错误结论"的负面结果。

**常见错误**

- ❌ 把依赖关系写成"三者相互关联、相辅相成" → 必须写成**单向依赖 + 原因 + 顺序不可换的反证**。
- ❌ 只写"本文采用 1B、2A、3C"而不写"依次" → "依次"二字是关键信息，丢了就无法对应依赖链。
- ❌ (2) 里的参数没有出处 → 评委无法判断这些机制是否真实存在于系统中。**每个参数都必须能指到源码行号。**
