# 四、系统实现

> 工作稿说明：本章对应导师版开题报告写作提纲第四章（知识库与经验检索、诊断编排、假设管理、证据工具、结论输出五个功能模块的实现）。本章只写"代码里实际是怎么做的"，含函数名与关键常量便于核对；效果、正确率与对照结论一律留到第五章，本章不出现任何成绩数字。文中未标注来源的行为描述均可按所给源码位置复核。

第三章给出了需求与分层设计，本章按同一套模块划分说明实现：每个模块先讲清楚它的输入输出，再讲关键处理，最后点出为满足第三章非功能需求而做的具体取舍。

## （一）知识库与经验检索

### 1. 文档入库

上传接口先做两道校验：扩展名白名单与文件头魔数比对，两者不一致直接拒绝，避免改后缀绕过。通过后把原始文件写入对象存储、元数据写入数据库，状态置为待处理，再投递异步任务。

处理逻辑写成一个不依赖框架的纯函数 `process_document(doc_id, progress=None)`（`src/worker/tasks.py`），内部按"解析 → 分块 → 向量化 → 写向量库 → 更新状态"顺序执行；Celery 任务 `process_document_task` 只是它的薄封装。这样拆分的原因是消息队列可能不可用：没有队列时同一函数可被同步路径直接调用，功能降级但不缺失。文档状态用四个值表示：0 待处理、1 处理中、2 完成、3 失败，失败可单独重试或批量重试。

解析按格式分流（PDF 用 PyMuPDF，其余走统一文档解析器），分块采用固定长度加重叠（默认块长 1000 字符、重叠 200），重叠的作用是避免答案刚好被切在块边界上。分块内容与页码信息一起入库，这是后面能在回答里标注"第几页"的前提。

### 2. 检索与重排

检索采用双路融合（`src/retrieval/hybrid_retriever.py`）：向量路走向量库做语义检索，关键词路走 BM25 做字面匹配，两路结果用倒数排名融合（RRF）合并，常数取 60，某条结果得分按 `1/(60+排名)` 累加。选 RRF 而不是加权求和的原因是两路分数量纲不同，RRF 只用排名，不需要调权重。BM25 索引不预建，首次检索时从数据库拉取分块懒建并缓存——小规模知识库这样做省掉一个独立的索引维护流程。

融合后如启用重排（默认启用），把候选交给重排模型按"与问题的相关性"重新打分，取前 5 条（`src/retrieval/reranker.py`）。重排是可选增强：开关关闭、接口返回非 200 或抛异常，一律退回按原顺序取前 5 条，不让重排服务的稳定性影响主链路。检索阶段先多取（启用重排时取目标数的 2 倍）再重排，给重排留出选择余量。

### 3. 问答链路的意图分流

问答入口在进入模型之前先做一次轻量判断（`src/services/rag_service.py` 的 `_quick_intent_check`）：短问句且只含问候语（你好、谢谢、再见一类）直接按闲聊回答；含诊断类词（cpu、内存、磁盘、超时、oom、报错等）标为诊断意图；其余交给问题分析器判定为知识型问题。分流的意义是避免"你好"这类输入也触发一轮检索与重排。

知识型问题走检索增强路径：拼上下文时按"段落 n（标识）"编号组织检索片段，提示词要求答案基于所给上下文、信息不足时明确说"根据提供的信息无法回答"、并引用相关段落编号。多跳开启时（默认开启，最大 3 跳）会根据子问题再检索一轮，去重合并后统一重排。

### 4. 经验资料的单独通道

诊断链路需要的"排查经验"与知识库问答不是一回事：前者来自 runbook、故障手册、历史案例，用途是提示"这类现象通常该看哪里"；它不能冒充现场事实。实现上单独一个模块（`src/agent/aiops/local_retrieval.py` 的 `retrieve_local(query)`）：把查询词切成词元后对 runbook 文件打分排序，支持 JSONL 索引、CSV/Parquet 表格与本地文本目录几种来源，输出带文件名的片段。

规划节点把这批经验放进"配置与排查参考资料"，并在提示词里写明**"不是现场证据，不扩大工具权限"**（`src/agent/aiops/planner.py:313-316`）。同时给经验条目打上知识库标记，使其不能进入现场证据索引——这一条是硬约束：如果经验片段能进证据索引，报告就会把"手册里说可能是端口错配"当成"现场观察到端口错配"，正是第三章 NFR-02 要禁止的情形。

## （二）诊断编排

### 1. 状态与图

诊断用一个 `StateGraph(PlanExecuteState)` 实现（`src/agent/aiops/graph.py:158-219`）。节点四个：规划 `planner`、执行 `executor`、再规划 `replanner`，以及仅在受控终端场景追加的终端复核节点；边为"规划 → 执行 → 条件分支（继续 / 收束）"。状态字段分两类：`plan`、`past_steps`、`raw_evidence`、`response` 为基本字段，`diagnosis`、`investigation_memory`、`hypothesis_space` 等为可选字段。`past_steps` 与 `raw_evidence` 用追加归约（`operator.add`）声明，保证多步执行不会覆盖前序结果。

这里有一处容易踩的坑值得记录：`src/agent/aiops/state.py` 顶部专门警告不要在该文件加 `from __future__ import annotations`。因为加上之后 `Annotated` 的元数据会被字符串化，LangGraph 读不到注入的归约函数，`past_steps` 的"追加"会静默退化成"覆盖"——不会报错，只是执行历史只剩最后一步。这个坑在状态文件里以注释形式保留。

### 2. 规划节点

规划节点（`planner`）的职责是把用户问题变成有序检查列表，实现上分四步：

第一步加载工具。工具清单来自各个 MCP 进程，加载失败不抛异常，而是记录下来继续——没有工具时规划仍然产出计划，只是后续执行会走缺证据路径。若诊断线程带用户标识，额外挂一个"读取本次运行证据"的工具，使模型能回看已经取到的原始证据片段。

第二步做确定性的首观测。当现场探针启用时，规划**先由程序**调用一次清单与证据列举（各 15 秒超时），把结果作为初始现场交给模型，并据此做目标解析（`resolve_target`）。这一步刻意不由模型决定：如果让模型自由选择第一次调用，不同轮次的起点不同，实验就不可比。目标解析返回"无法唯一确定"时，规划直接终止并给出候选列表，结论定为"无法定位"，避免在没有锁定对象的情况下继续消耗调用。

第三步取经验资料，把参考资料、现场目录、目标解析结果拼成参考上下文。

第四步让模型产出计划。计划是字符串列表，每条是一句自然语言任务描述；产出后过一遍 `_sanitize_plan_steps`，把不在当前工具清单里的步骤剔掉，防止模型凭想象编出并不存在的工具。

### 3. 执行节点

执行节点每轮只取计划的第一项（`src/agent/aiops/executor.py:693` 起）。关键处理有五处：

- **把真实标识符塞给模型**：从已有执行历史里抽出真实的容器、服务、日志主题等标识，作为参数提示，减少模型编造标识符（`_extract_real_identifiers`）。
- **参数守卫**：调用工具前过一遍守卫链（`src/agent/aiops/tool_guards.py` 的 `run_guards`），包括主题对齐守卫（把与当前目标无关的查询词剔除）、泛词过滤守卫（把"服务""系统"这类无区分度的词从检索关键词里去掉）、指标与变更的时间窗重锚守卫（模型给的时间范围若明显偏离本次请求窗口，重新锚定到请求时刻附近）。守卫可单独禁用，便于定位问题。
- **确定性兜底**：若这一步的任务文本要求查日志（含 `search_log` 或"日志"字样），但模型这一轮始终没有产出日志结果，则用已知的真实主题强制调一次（`_forced_search_log`）。这是为"证据链不因模型工具选择不稳定而断裂"加的保险，属于程序对模型行为的补位。
- **异常降级**：工具异常不中断整轮诊断，而是把错误转成一段文本作为这一步的结果写回，同时保留已取得的原始证据（`_sanitize_error`）。这样一次工具失败只丢一条证据，不丢整场诊断。
- **原始证据留存**：每步既写"给人看的摘要"到 `past_steps`，也把工具原始返回写进 `raw_evidence`。两份分开存的原因见第（四）节。

### 4. 再规划节点与三个结束条件

再规划节点本身很薄（`src/agent/aiops/replanner.py`），只做两件事：把决定委托给当前生效的策略，然后在收束时调用报告收尾。策略选择有一个容易误判的地方：注入的策略类名不等于实际执行的算法。`replanner` 里显式判断——当状态标记为自主调查、且注入的是默认策略或旧动态分类策略时，实际执行的是 `InvestigationStrategy`。因此阅读代码时不能凭"注入了 DynamicClassificationStrategy"就断定现场跑的是旧动态分类算法。

三个结束条件在实现上的落法各不相同：**"证据足以支持结论"** 由决定函数在判定候选已确认或已定位时置停止原因；**"没有可继续的检查项"** 由检查契约校验发现提议的检查不可执行（缺字段、参数与已知标识冲突、重复查同一绑定规则）时触发；**"达到调用次数上限"** 由程序侧的计数与预算保证，是唯一不依赖模型判断的硬边界。三者都会写入停止原因并进入报告，读者能看到本轮为什么停。

### 5. 事件流与检查点

诊断过程通过事件对象对外发布（`src/agent/aiops/events.py`），共九类：计划、步完成、状态、草稿、报告、待复核、完成、错误、证据。每类都是带类型字段的字典，由 `make_*` 工厂函数构造，接口层统一包成 `{"event": "message", "data": ...}` 的流式帧下发；图执行结束后再补一个用量事件（模型调用次数、输入输出 token、费用估算、耗时）。

检查点用 LangGraph 的持久化机制，按会话线程标识保存，进程内用内存保存器，配置了路径时用 SQLite 保存器。检查点的作用是支持"挂起后继续"：需要人工复核时，图在生成草稿后挂起，恢复时按线程标识读回状态并继续执行。检查点与运行记录是两套数据，前者服务于图，后者服务于人（见第（五）节）。

## （三）假设管理

### 1. 候选的表达

候选原因及其检查在 `src/agent/aiops/strategies/investigation.py` 里用一组数据模型表达：每个候选带状态（支持、已排除、不可得、未决）、支持与反对的依据、待核实事项，以及若干"观测条件"——条件是可用现有证据判定的谓词，而不是自由文本。检查提议带工具名、参数与它要验证的条件。

这样设计的原因是可判定性：如果候选只有一句自然语言描述，系统无法判断"这条证据支持它还是反对它"；把候选拆成"身份（哪个对象）+ 条件（什么现象）"之后，证据能用程序判定是否命中条件。

### 2. 保护与矛盾触发

两项机制各由一个开关控制，默认都开启。

**候选保护**：候选带上"出生步"字段，只有当已经推进的步数达到保护步数（默认 2）之后，才允许因证据不足而淘汰它。效果是给刚提出的候选留出检查窗口，避免模型在第一轮就因为"还没证据"把正确候选丢掉。

**矛盾触发**：当新证据与当前主要判断冲突时，机制会插入针对性的补充检查。实现上把"矛盾"限定为**系统可派生的真实冲突**（例如同一服务的配置快照与运行日志对同一字段给出不同值），而不是模型自己写的"待核实说明"。这一区分来自一次真实的判定缺陷：早期把模型写的说明性文字也算作矛盾，结果一条"待核实"备注就能否决整轮结论。

### 3. 决定函数的处理顺序

再规划的决定不是直接把模型输出当成结论，而是经过一条固定顺序的处理链（`decide_from_evidence` 与 `_apply_investigation_mechanisms`）：

1. **解析候选身份**：把提议里的候选与已知对象对齐；若一个候选的条件描述指向 A 对象、身份却挂在 B 对象上，则整轮提议作废（整轮原子拒绝，而不是删掉冲突的那一条）。
2. **校验引用**：提议里每条引用必须能在本次证据集合中找到，找不到的引用被移除或使该提议判为无效。
3. **校验候选**：候选是否绑定到具体条件、条件是否可由现有证据判定（谓词已核验），不满足则视为"不足以支持结论"。
4. **识别空壳结论**：结论文字是占位或重复上一步的表述时，不算收束（`empty_terminal_claim`）。
5. **校验检查契约**：提议的下一步检查必须带齐字段、参数不与已知标识冲突、不是重复查同一绑定规则；不满足则不能作为"继续"的理由。
6. **应用机制**：在以上校验通过的基础上，再叠加保护与矛盾触发的调度，并**记录机制是否获得机会、是否改变了原定顺序**——这一记录是第五章判断机制有没有起作用的数据来源。
7. **定级**：按证据状态给出三档结论之一——已确认直接原因、已定位故障层但原因待核实、无法定位；并给出停止原因与未决问题。

处理链的顺序本身是设计决策：**空壳拒绝必须排在"缺必需证据则降级"之前**。否则一个已给出完整结论、只是没写补充检查的提议会先被降级成"继续补查"，然后被下一轮的空壳提议接手，最终丢掉本已得到的结论。

### 4. 结论分级

三档结论的判定依据不同：**已确认直接原因**要求存在能直接解释现象的现场证据（例如生命周期记录里存在"启动 → 收到停止请求 → 进程退出"三件套，且与请求时间对应），且证据间无未解释冲突；**已定位**要求对象与故障层明确、但缺少把原因钉死的那条证据，此时必须列出未决问题与所需补充检查；**无法定位**用于目标解析失败或候选全部被否的情形。

定级后不再回写为更高等级：一轮诊断只有一个终态，避免出现"报告说已确认，附注说待核实"这种自相矛盾的输出。

## （四）证据工具

### 1. 工具以独立进程提供

四类查询能力各由一个独立进程通过 MCP 协议暴露：监控指标（8104）、日志（8103）、知识检索（8105）、变更记录（8106），另有诊断数据（8107）与现场探针网关（18767），受控终端（18766）默认关闭。主服务按配置加载工具清单（`src/agent/aiops/tools.py` 的 `load_agent_tools`）并缓存。

进程隔离带来一个直接好处：某个工具没起来，在系统里表现为"这个工具不在清单里"或"调用返回错误"，而不是主流程异常。这使第三章 NFR-03（可降级）成为可实现的需求，也使第五章"工具部分不可用"成为可设计的实验条件。

### 2. 可用性显式标注

工具可用性由 `src/agent/aiops/evidence_sources.py` 统一计算：`source_availability` 给出每个证据源的状态，`missing_source_labels` 给出缺失清单，`availability_warning` 与 `format_availability_note` 把这些内容格式化成可读提示，随状态事件与报告一起下发。

这里贯彻第三章 NFR-02 的纪律：**配置了真实后端但不可达时不回退模拟数据，而是标注为不可用**。系统里保留了模拟后端仅用于离线测试，生产路径上不允许"真实后端失败就悄悄换成 mock"。

### 3. 调用记录与证据入库

每次工具调用都记录三样东西：调用条件（工具名与参数）、返回结果、调用状态（成功/失败/超时）。运行数据必须带所属服务与采集时间，否则无法判断它是否能说明"现在"的状态。

证据入库走 `run_store.add_evidence`（`src/agent/aiops/run_store.py:223`），写入四类信息：稳定的证据标识、原始引用指针、原始内容摘要（哈希）、新鲜度时限。标识稳定是为了让报告能引用、让去重能生效；原始指针与哈希是为了审计时能回查原文并判断有没有被改动；新鲜度时限是为了防止用过期快照支撑当前结论。

### 4. 去重与"不重复加分"

第三章 FR-19 要求同一结果不得重复计入以提高可信度。实现上有三处对应：一是证据索引按键归并（同一服务、同一字段、同一来源哈希只留一条）；二是重复查询检测，同一工具同一参数在无新证据时重复调用会被记录为"无新证据的重复"并阻止其进入判断依据（`probe_checks.py` 的 `_log_repeat_has_new_evidence` 与 `check_progress`）；三是未决问题按缺口标识去重，避免同一个未查清项在报告里出现多次被读成"多个问题"。

### 5. 证据读取与权限

模型看到的证据是摘要，需要原文时通过"读取本次运行证据"工具按需取片段（`src/agent/aiops/evidence_reader.py`）：参数校验限定标识格式、偏移与单次长度（默认 4000 字符），并按用户标识过滤，跨用户的证据读不到。这条设计把"模型上下文有多大"与"证据有多少"解耦：证据可以很多，模型每次只取需要的那一段。

## （五）结论输出

### 1. 报告由结构化组件拼装

报告不是模型直接写的一段文字，而是先由 `build_bundle`（`src/agent/aiops/reporting.py:133`）把诊断结果整理成结构化组件：结论类型、影响范围、焦点对象、关键事实（每条事实带证据标识）、证据支持的解释、人工处理建议（含操作前提、风险、处理后验证步骤、建议依据）、校验提示、阻塞说明、未决问题、限制、停止原因，以及经验资料引用。

随后由 `rule_layout` 给出组件顺序（不调模型时的默认路径），或在显式开启付费会话时由模型给出排序。`validate_layout` 再校验排序结果：不得重复、不得出现集合外的标识，且针对焦点对象的处置建议必须排在后续检查之前。最后 `render_report` 按固定版式渲染成文本，开头区分两档结论的措辞——已确认直接原因时写"诊断结论（已确认直接原因）"，否则写"已定位故障层"并明确"优先处理对象尚不能确定"。

### 2. 引用校验与失败降级

报告渲染前有一道硬校验：每条引用必须能在本次证据集合中找到，且引用文字必须是该证据原文的子串。校验失败不是删掉个别句子，而是整份报告降级（`reporting.py:403-405`）：状态记为失败，失败原因写 `report_source_reference_invalid`，正文替换为"报告证据核验未通过，不能可靠整理处置建议。调查原结果和证据保留在详情，需核对引用后再处理。"

这样处理是刻意的：部分正确的引用比没有引用更危险，读者会默认整份报告都核实过。宁可交一份"未通过核验"的说明，也不交一份"大部分对"的报告。

### 3. 模型在结论阶段的权限被压到最小

模型对报告的唯一作用对象是"核心事实的排序"：输入是已核验的核心事实投影，输出必须包含全部允许的事实标识、每个恰好一次，不得新增事实、结论或命令（`CoreFactOrder` 与 `_model_layout`）。文字表述、对象顺序、处置动作都由程序保留。

模型参与还需显式开启：只有在付费会话上下文中（`report_model_session`）才会调用模型，并先以独占方式创建一个尝试标记文件；文件已存在说明上次尝试未走完，此时直接用规则排序而不重试。这一机制的目的是防止"崩溃后重跑导致重复付费"，对应第三章 NFR-04（可控开销）。无论模型是否参与、成功或降级，报告记录里都会留下模式（规则/模型）、状态、输入哈希与报告哈希，供后续核对。

### 4. 人工建议与"未执行"声明

处置建议来自 `src/agent/aiops/recommendations.py`：对每个焦点对象给出建议动作、操作前提、风险与处理后验证步骤，并按对象映射与现场解析结果做裁剪。报告里这一节的标题固定为"人工处理建议（待人工核对，尚未执行；不作为根因证明）"——系统不执行任何写操作，建议也不是根因证据。

报告末尾固定保留"剩余未知"与"停止原因"两节：前者说明更深的原因尚未确认、未核验的因果解释仍然保留；后者说明停止是"直接原因与请求证据链已核验"还是"现有候选检查已完成或受阻"，并明确"仅覆盖系统当前可识别的有限检查，不代表所有可能检查已穷尽"。

### 5. 运行记录与查询接口

每次诊断在运行表里留一条记录（`run_store.py`），状态机为运行中 → 待复核 → 批准/拒绝 → 完成，异常路径进失败；每次决策可选落一条步快照（默认关闭，开启后按步记录规划/执行/再规划的关键信息）。审批记录单独成表，记评审人、动作与指令。

对外查询接口五个：运行详情、证据清单、单条证据（审计员可读原始引用）、步快照、探针目标状态。删除与写操作一律不通过查询接口暴露；证据原文只对审计角色开放，普通用户只能看到摘要。这组接口是第五章"报告可审计"判定的实现基础。

## 本章小结

本章按五个功能模块说明了实现：入库与检索用"双路检索 + 可选重排 + 经验资料单独通道"，把经验与证据在数据结构上分开；诊断编排用三节点状态图，计划由模型生成、执行有程序侧补位、结束条件三条中有一条是硬边界；假设管理用"身份 + 条件"的可判定表达，保护与矛盾触发各由开关控制，决定函数按固定顺序校验后定级；证据工具以独立进程提供并把可用性显式标注，证据带稳定标识、原始指针与新鲜度；结论输出由结构化组件拼装，引用校验失败则整份降级，模型在结论阶段只被允许排序核心事实。

贯穿五节的一条线索是同一个取向：**把"模型说什么"与"系统能证明什么"分开**。计划、候选与建议可以由模型提出，但证据必须由工具给出、引用必须能对上原文、结论等级必须由证据状态推出。这一取向在第五章会转化为具体的判定口径与失败案例。
