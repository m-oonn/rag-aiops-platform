# 一、绪论

> 工作稿说明：本章对应导师版开题报告写作提纲第一章（研究背景及意义、国内外研究现状分析、研究目标与适用边界）。文献归纳只到"该文献研究了什么层面"，不对单篇的实验设置作评价，逐条引用位置见第二章与《参考文献对照-导师版36条》。本章不含任何实验结果。

## （一）研究背景及意义

### 1. 故障诊断的门槛从"分析能力"移到了"工具与经验"

微服务架构把一个单体应用拆成若干可独立部署的服务，好处是开发与扩容更灵活，代价是**一次对外可见的异常可能来自任意一层**：入口服务、网关、下游应用、数据库或配置。参与者只要有一个接口变慢或不可用，用户看到的就是"系统坏了"，而运维要回答的是三个更难的问题：哪个服务坏了、坏在哪个环节、为什么坏。

回答这三个问题需要数据。工业界的做法是建立可观测性体系：采集指标、集中日志、串联调用链，再在数据上做异常检测与根因定位。这条路线在大型互联网公司已经相当成熟，也形成了完整的工具链[1][2]。

但对另一类使用者，这条路线并不成立：**缺少专职运维支持的小公司和个人开发者**。他们没有独立的可观测平台，日志散落在几台机器上，指标可能只看得到最粗的资源占用，调用链大多没有接入；出了故障，能用的手段是登机器、看日志、凭经验猜。对他们而言，问题不是"检测精度不够高"，而是**没有一套能把零散数据组织成推理过程的东西**。故障诊断的门槛已经不是"会不会分析"，而是"有没有工具与经验"。

### 2. 大语言模型改变了可用的工具形态

大语言模型带来两个直接变化。第一，**它能把自然语言问题转成对工具的一次次调用**：模型读到"接口 503"这样的描述后，可以决定去查某个服务的进程、再查最近的配置变更、再看日志里有没有对应的请求记录。这种"推理—行动—观察"的交替形态在 ReAct 一类工作中被明确[21]，在运维诊断领域也已经出现了把日志、指标、代码检索封装成工具交给模型调度的系统[24][25]。

第二，**它能把排查过程讲出来**。传统根因定位方法输出的是一个排序列表，运维还得自己去理解为什么是这一项；而语言模型可以在给出结论的同时说明"我看到什么、我查了什么、我还缺什么"。

这两点恰好对应前述缺口：把零散工具组织起来的能力，以及把过程讲清楚的能力。但这两点也带来了新问题——模型会编造，而且编得很像真的。

### 3. 真正的困难是"不确定"而不是"不会推理"

把大模型放进诊断链路之后，实践中暴露的问题集中在三处，且都不是"推理能力不足"：

**第一，模型很容易把工具报错当成结论。** 日志里出现一条连接失败的报错，模型可能直接回答"下游服务挂了"。但这条报错只说明某次连接失败，既不能区分是下游真挂还是配置指向了错误的端口，也不能排除网络或权限因素。开题报告把这一条写进了系统要求："若日志显示连接失败，系统不会直接将该报错视为最终原因，而是进一步查询相关服务的状态及近期配置变更。"

**第二，模型在证据不足时倾向于给出完整答案。** 幻觉现象与检测方法已有系统讨论[33][34]；模型能否准确表达自身置信度，也有实证评估表明其自评并不可靠[35]；在信息不足时"选择不回答"的能力与评测，见弃答方向综述[36]。对诊断系统来说，这不是语气问题而是正确性问题：一个把"我不确定"说成"就是这个原因"的系统，比一个不给答案的系统更危险。

**第三，工具会缺失，而缺失会被误读。** 运维环境里总有查询工具不可用的时候：日志平台在维护、指标库连不上、变更系统没权限。此时如果系统悄悄退回模拟数据或用"未发现异常"代替，结论就会沿着错误的方向走下去。本文开发过程中确实发生过一次：模拟日志里带有内存溢出的堆栈片段，模型据此给出了与真实原因无关的结论，整轮观测因此作废。

这三点共同指向一个结论：对这类面向小系统的诊断工具，**比"推理得多准"更关键的是"能不能说清楚自己知道什么、不知道什么"**。

### 4. 研究意义

**工程意义**：本文把"诊断过程可审计、结论有等级、缺失有记录"做成系统的一等约束，而不是事后补的说明文字。三条具体约束落到实现上是可检验的——引用必须是证据原文子串、结论只允许三档、工具缺失必须显式标注。这组约束可以直接被同类小系统复用。

**方法意义**：本文不追求更强的搜索策略或更大的模型，而是研究两个在诊断过程中容易被忽略的环节：候选原因为什么不该被过早淘汰（候选保护），以及新证据与现有判断冲突时该做什么（矛盾触发）。这两个环节在大模型智能体里通常被"继续调工具"掩盖掉了。

**教学与实践意义**：完整实现与实验证据都留在仓库中，包含可重复的判定规则回归语料，可供后续研究直接对比。

## （二）国内外研究现状分析

本节按"传统方法的证据来源 → 大模型智能体路线 → 不确定性与诚实性"三条线索归纳。需要说明的是，本文只在这些文献的**问题定位**层面引用它们，不依赖其具体数值结论。

### 1. 传统根因定位：按观测数据分路推进

微服务根因定位的研究已经形成按观测数据类型分野的格局，国内外综述对此有系统梳理[1][2][3][4]。

**日志方向**起步最早，方法脉络清晰：从把日志解析成模板再检测序列异常的 DeepLog[8]，到模板与语义结合的无监督检测 LogAnomaly[9]，再到针对日志本身不稳定（版本迭代导致日志文本漂移）的鲁棒检测 LogRobust[10]。国内综述对这一支的演进有完整归纳[5][6][7]。日志的优点是信息量大、几乎不需要额外埋点；缺点是格式不统一、与故障的因果关系弱——一条报错往往只是现象。

**指标方向**依赖服务依赖图。MicroRCA[11] 用服务间的调用关系图把异常指标归因到具体服务；MicroRank[12] 用扩展谱分析定位时延问题。指标的优势是数值化、可统计；劣势是粒度粗，只能指到"哪个服务"，指不到"哪个环节"。

**调用链方向**提供最细的因果证据。基于 trace 的多维定位[17] 与控制流分析下的性能建模[18] 都在利用"一次请求经过了哪些环节、每个环节耗时多少"这件事。调用链的问题是采样与埋点成本，小系统往往没有。

**多源融合**是当前主流：Eadro[14]、Nezha[15]、HeMiRCA[16] 都在把日志、指标、调用链甚至代码变更合起来判断。**依赖与影响图**方向则关注结构信息，包括服务依赖发现综述[13] 与基于多层次影响图的定位方法[19]。**变更视角**的问题意识最接近本文关注的一类现场：系统的异常经常由近期的一次变更引入，余广坝等的工作专门研究面向大规模在线系统的根因变更识别[20]。

这一支工作的共同前提值得点出：**它们都假定观测数据是完整的、可离线训练模型的、且输出是一个根因排序**。这个前提在大型系统里成立，在本文面对的小系统中不成立——数据是零散的、没有标注、也没有训练集；更关键的是，输出一个排序并不能告诉运维"下一步该查什么"，更不能告诉运维"这次结论有多可靠"。

### 2. 大模型智能体路线：把查询变成动作序列

把大模型作为诊断的执行者，是近三年发展最快的方向。康俊驰等的综述对这一支做了系统整理[28]。

按"模型在链路中承担什么"可以分三类。

**第一类，模型调度工具。** RCAgent[24] 与面向云事故的自动根因分析[25] 都把日志、指标、代码检索封装成工具，由模型决定查什么、怎么查，把模型的推断建立在工具返回之上。Xpert[26] 换了个角度：不直接做诊断，而是用历史工单生成查询建议，降低人工排障时的检索成本。OScope[27] 强调专家经验应进入诊断流程，而不是被模型先验替代——这一条与本文"经验资料与现场证据分开"的处理直接相关。

**第二类，模型组织推理结构。** ReAct[21] 的"推理—行动—观察"交替循环是所有工具调用式智能体的基础形态；Reflexion[22] 引入跨试验的语言化反思，让智能体把失败经验写成文字留给下一轮。在诊断场景里，LATS-RCA[31] 把树搜索用于根因分析，用并行展开代替单线试探；Hypothesize-then-verify 一类工作[32] 提出"先集中提出假设、再逐条验证"的路径并讨论并行化。

**第三类，模型配合检索。** 检索增强生成[23] 让模型在生成前先取回外部资料，把答案建立在可追溯的文本上。运维场景的知识形态（故障手册、历史案例、变更记录）天然适合这种方式。

这一支工作解决的是"能不能查到、查得快不快"，本文关注的则是另一面：**在证据有限、工具可能缺失的条件下，系统能不能不把不确定说成确定**。因此本文在结构上保留了这三类工作的基本形态（工具调用、状态图编排、检索增强），但把机制重心放在候选状态的维护、补充检查的触发条件与结论的定级上。

### 3. 不确定性与诚实性：从"答对"到"知道何时不该答"

**经典诊断理论**早就给出了"如何在信息不完整时推进诊断"的框架。基于模型的诊断把"什么可能坏了"表示为候选集合，用与观测冲突的假设逐一排除，其经典形式是多故障诊断与冲突集[29]；决策论排障进一步把"下一步查什么"变成有代价的决策，按期望收益选择下一个检查[30]。

这两个框架对本文有两点直接影响：诊断的对象应是**候选原因的集合**而非单个猜测；检查顺序本身是一个**需要记录理由的决策**。不过本文没有采用[30] 的量化路线——既没有可靠的先验分布，也没有把"检查代价"标定成可比数值，因此只借用其思想，不宣称实现了决策论排障（这一点在第五章局限中重申）。

**大模型的不确定性**则是另一类问题。近年研究一方面系统整理了幻觉的成因与表现形式[33]、检测方法[34]，另一方面评估了模型能否准确表达自身置信度，结论偏谨慎[35]；在无法回答时选择弃答（abstention）的策略与评测也已有综述[36]。这些工作共同支持一个判断：**让模型自己报一个置信度数字，在缺乏标定的条件下并不可靠**。

本文据此做了一个取舍：不给数值置信度，而是给**由证据状态推出的等级**。等级的判据是程序可检验的（有没有能直接解释现象的证据、证据之间有没有未解释的冲突），而不是模型的自我评估。

### 4. 现状小结与本文切入点

把三条线索放在一起，可以看到一个共同的空白：

- 传统方法**假定数据完整**，输出根因排序，不回答"缺了某项数据该怎么下结论"；
- 大模型智能体路线**假定工具可用**，把重点放在查得更准更快，对"查不到"的处理往往是重试或跳过；
- 不确定性研究**多在大模型自身层面**，讨论模型如何表达不确定，较少落到"一个诊断系统应该怎样组织证据、怎样定级、怎样把待核实项交给人工"这一层。

本文切入的正是这个空白：在**小型系统、单一主要故障、工具可能部分不可用**的条件下，研究一个诊断智能体怎样把证据组织成可审计的推理过程，并在证据不足时如实交出"已知 / 待核实 / 所需补充检查"三部分内容，而不是交一个看起来完整的结论。

## （三）研究目标与适用边界

### 1. 研究目标

本文的目标是**设计并实现一个基于 LangGraph 的 AIOps 根因诊断 Agent**，使其在小型微服务测试环境中，能够：

1. **组织诊断过程**：把用户的一句话描述转成有序的检查计划，根据新证据调整后续步骤，并把每一步的依据与结果留存；
2. **管理候选原因**：为每个候选记录支持依据、反对依据与待核实事项，在限定轮数内保护证据尚不充分的候选，对有明确反证的候选予以排除，在新证据与主要判断矛盾时安排补充检查；
3. **组织证据**：通过工具获取指标、日志、变更记录与排查经验，记录每次查询的条件、结果与状态，标注数据所属服务与采集时间，并在工具不可用时记录缺失而不是替代；
4. **输出有等级与出处的结论**：报告说明可疑服务、候选原因及各自依据，区分当前运行数据与历史资料，证据不足或矛盾未解决时标为待核实并列出需补充的检查；
5. **接受检验**：上述机制各自配有独立开关，以便在固定条件下做对照与消融；判定规则配有离线回归语料，使"改判定逻辑不破坏已通过的轮次"成为可自动执行的门禁。

目标表述刻意不含"提高诊断准确率"这类比较性承诺。本文能承诺的是过程性质（可审计、有等级、缺失有记录），而不是效果性质；效果以第五章的实测为准，且样本量限制已在该章说明。

### 2. 适用边界

**适用条件**：

- **系统规模**：3 至 5 个服务的小型微服务系统，服务间依赖关系可登记；
- **故障形态**：由**单一主要故障**引起的异常。本文已实现的故障类型为服务停机与配置错误两类；延迟类故障尚未提供注入能力（第五章说明）；
- **数据条件**：指标、日志、变更记录可通过接口查询（或经现场探针采集），不要求完整的调用链；
- **使用者**：缺少专职运维的小团队或个人开发者，接受"系统给出待核实的诊断建议、由人确认"的协作方式。

**不适用条件（明确排除）**：

- **多故障并发**：同时存在多个相互独立的主要故障。本文的候选管理按单一主要故障设计，并发故障会让"候选排除"的语义失效；
- **大规模系统**：服务数量达到数十个以上时，逐服务排查的调用次数与费用不可接受；
- **强实时场景**：单轮诊断包含多轮模型调用与工具查询，耗时以分钟计，不适合秒级止损；
- **要求形式化保证的场景**：本文不提供"诊断结论正确"的保证。报告明确写明未确认的更深原因、未核验的因果解释与检查覆盖的有限性；
- **自动处置**：系统不执行任何写操作，只输出建议；所有处置需人工核对后执行。

### 3. 与开题报告承诺的对应

导师版开题报告提出五个功能模块与两组算例、四个维度的验证安排。本文的对应关系是：五个模块在第三章按 M1–M5 落实并在第四章给出实现；验证安排见第五章，其中"隐藏故障场景端到端"与"工具降级条件"两组算例对应第五部分的两类实验条件，"机制有效性、可解释性、鲁棒性、诚实性"四个维度分别对应机制开关对照、证据引用可回查、工具缺失下的可降级、结论等级与待核实项的准确性。

**本轮尚未覆盖的部分**如实列出：延迟类故障未实现注入；"工具部分不可用"的系统性实验尚未开展（单场条件准备已在测试环境中完成）；八场真实诊断的人工语义审核仍在进行，因此"诊断正确率"尚无取值；假设保护机制在已完成的真实付费轮次中尚未获得触发机会，矛盾触发的机会数与改向数已在第五章如实给出而未做统计推断。

### 4. 本文结构

第二章介绍相关技术：大模型工具调用、检索增强与向量检索、基于状态图的流程编排、故障诊断中的候选原因与证据。第三章给出需求分析与总体设计：27 条功能需求、7 条非功能需求、五层架构、部署视图、数据流与模块划分。第四章按五个功能模块说明实现。第五章给出测试环境、功能测试、不同工具条件下的诊断效果、对照实验与运行开销，并讨论局限与后续工作。

## 本章小结

本章说明了选题的由来：微服务把故障定位的成本转嫁给了使用者，而缺少专职运维的小团队既没有可观测平台也没有排障经验；大语言模型让"组织工具"与"讲清过程"成为可能，但也带来了三类新风险——把报错当结论、把不确定说成确定、把工具缺失读成正常。围绕这三类风险，本章把研究目标限定为过程性质的可审计、有等级、缺失有记录，并明确排除了多故障并发、大规模系统、强实时与自动处置四类场景。
