# 有检查继续查，停止逐项说明缺口（2026-10-29）

用户要求：能查清的应继续查；未查清的如实说明理由。这里的“查清”依据实际工具、允许对象、原始证据与因果验证能力，不把模型高信念或故障层定位当作调查结束条件。

## 实际缺口

既有策略已强制核查失败loopback依赖的监听，但模型未给顶层next_check、却在当前关键候选check中保留了有效检查时，调查仍可能直接出报告。监听请求超时且没有有效观测时，策略又会重新安排同一请求。公开因果文本替换还会丢掉具体限制，只剩“不能确认该因果解释”。本轮七条新增反例先失败，确认以上问题；四组参数化反例分别计数。

## 调查与停止流程

1. 沿既有 `decide_from_evidence` 核对新鲜现场、业务范围、候选身份和两项机制。
2. 失败白名单loopback依赖尚无同端口快照时，保留精确监听检查；同参数最近已有失败/不可用记录时不原样自动重试。
3. 模型未提出下一步时，检查**本轮仍活跃的关键未决候选**。候选已有有效check、工具存在、对象范围允许、该步骤尚未完成且未失败时，把检查交给同一执行器。
4. 模型已经选了检查、身份冲突或当前必要预期被反驳时，不用普通补查绕过已有调度/校验。被遗漏或淘汰的候选仍由假设保护处理，普通补查不复活它们，也不伪造机制事件。
5. 停止报告逐项写“未查清问题＋实际阻碍”，并同步保存至现有 `diagnosis.unresolved_questions`、`limitations` 与调查记忆。区分工具未加载、对象未解析/超范围、具体调用失败、步骤已执行但问题未解决、步骤尚未执行，以及模型没有提供检查方案。模型说明的数据限制明确标为未独立核验，不能替它证明权限缺失。

下游TCP失败额外说明：本机端口快照是否取得、是否失败/截断、监听PID是否缺失，以及该依赖是否提供允许的服务/进程与日志映射。未返回host时写地址信息缺失，不能把它当远端。TCP拒绝不证明进程退出原因；读取了端口也不自动证明根因。

## 真实例子的正确推进方向

旧G11场只查6989连接，没有查6989监听。当前代码应补监听，再根据允许映射查进程与日志。原专用业务只把downstream公布为依赖，没有可用于该对象的进程/退出日志映射，故深层原因不能从入口python进程存在推断。这个缺口需要后续核对Probe及测试业务配置，而不是编造崩溃原因或重复连通探测。旧运行与人工审核保持原样，用户本轮对规则的要求不算对该场裁决。
