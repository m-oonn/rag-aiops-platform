## 预设故障答案核对

本轮配置场由控制器将专用业务 `app.mode` 的 `max_attempts` 设置为字符串 `invalid`。应用把该值转换为整数时抛出 `ValueError`，入口返回 HTTP 503；下游仍返回 HTTP 200。控制器源码和盲测记录用于事后答案核对，不伪装成 Agent 证据。

Agent 自己取得入口 503（`ev-ed936faeedc14483a0f7aedb8a3a9274`）、下游 200（`ev-9e353dc87941480ba48cfc03c4193848`）、应用 `ValueError` 日志（`ev-60471949a65845c2a3e988821c40bcd0`）和同源哈希的独立配置快照（`ev-088f404ca75c4e6eae06be93ba5808f4`）。因此，对预设的**直接故障位置**，Agent 定位正确；这些现场事实支持配置解析失败解释。日志与快照交叉一致仍不是独立因果复现，且不能识别谁在何时写入了配置。

原报告的问题是解释写得过泛，并把“更深原因未知”放在已观察到的非法字段和解析错误旁边，读者容易理解成根因完全没找到。重复出现的操作者历史缺口也加重了这个问题。人工处理建议适用于此夹具：确认当前值、人工改成业务允许整数、按应用方式生效，再分别检查下游和入口及新日志。用户改为 `5` 后，原人工窗口先超时并清理；之后免费重启相同专用业务，两个接口均 200。窗口超时、控制器恢复清理和用户修改后的重启复测分别保留。

策略最小回归现已要求报告明确列出 `max_attempts='invalid'`、`ValueError` 与 HTTP 503，解释日志和快照的证据边界，并只输出一次操作者历史缺口。同一历史输入的修后文本存于 `runtime/fault-pair-preexperiment-20261103-a/report-after.txt`；原报告未改。
