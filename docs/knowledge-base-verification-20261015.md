## 实测通过

- 运行配置使用 BAAI/bge-m3，向量维度 1024；embedding 兼容接口已配置，重排开启。本次未调用外部 embedding 或重排接口。
- SQL 中有 12 个知识库、203 个文档片段；运维排查库（ID 14）有 6 篇完成文档、8 个片段。
- 本地 vectors.npy 形状为 (17526, 1024)，元数据条数一致；唯一 ID 为 17151。17521 条标记 kb_id=0，5 条标记 kb_id=14。外部案例来源包括 TRAC-RCA 的 Cloudflare、Google、DigitalOcean 等 JSONL；这些是既有语料数量，不代表已审核有效案例数量。
- 用生产 BM25 从现有 SQL 文档片段中查询：CPU、磁盘空间不足、端口异常三个查询首条均为对应排查手册。这是少量人工烟测，不是检索准确率评测。
- 用已有文档的存储向量做相同向量检索，原片段相似度为 1.0；限定 kb_id=14 返回该库片段，限定不存在的 kb_id=999 返回空。此项验证本地相似度搜索和过滤，不证明自然语言在线 embedding 可用。
- 相关测试分两次执行：默认离线选择 7 passed、23 deselected；显式选择其余带 integration 标记的向量/混合检索与知识库接口测试 23 passed。这些测试使用 mock/内存数据库，不能当成外部服务集成验收。既有 PyMilvus 弃用提醒仍存在。

## 已复现的问题

1. SQL 与本地向量覆盖不一致：203 个 SQL chunk ID 只有 5 个出现在本地向量中；运维库 8 个片段只有 5 个有本地向量，CPU、磁盘、端口手册缺本地向量。本次 Milvus 未运行，因此无法核对远端是否另有这些记录。
2. BM25 加载范围有限：HybridRetriever 优先从 SQL 加载 203 条；SQL 非空就不会再合入 LocalVectorStore 的外部案例，故关键词侧没有覆盖本地大部分外部语料。
3. 降级缺口：注入明确的 embedding/向量异常后，HybridRetriever.retrieve 直接抛错，即使真实 BM25 对同一 CPU 查询有结果，也没有继续返回。该异常为受控故障注入，不是声称在线 embedding 当前实际已故障。
4. 无关召回：不限定库查询“数据库连接被拒绝”会混入 AI 编程报告；限定运维库查询“量子纠缠实验怎么做”仍返回运维片段，第一条 BM25 归一分为 1.0。归一分只是候选相对排序，不能当可靠度。
5. 来源追溯不足：SQL 加载 BM25 时只保留 kb_id，缺 filename/page 等元数据；经 MCP 格式化可能显示 unknown。未验证在线重排后来源是否完整。
6. 默认经验检索未配置 EXPERIENCE_KB_IDS 白名单，存在测试资料与运维案例混检风险。已有 375 条重复向量 ID，尚未做全文去重与案例有效性审核。

## 应完成的验收

先补齐失败降级、语料覆盖、来源元数据和检索范围，再使用独立输出目录验证：真实新文档解析入库 → 在线 embedding → 混合检索/重排 → 引用回到原文 → MCP 与 Agent 联调。故障验收应保留知识库入口，让模型只收到症状，结合真实现场证据验证假设；必须包含正常场景、无关问题/无答案场景和手册与现场不一致的场景。知识内容只能作为排查参考，不能冒充本次机器证据。

在线 embedding、重排、回答生成和真实 Agent 调用可能消耗额度，需要沿用已授权范围；本次没有扩大之前隔离场景的费用授权。
