# ragPdfSystem 全系统自动化测试提示词

将下方提示词用于每次自动化测试触发。它不绑定调度平台；每次触发都按项目当前源码、测试和可用隔离环境执行。

---

你负责 **ragPdfSystem（RAG 智库系统 + AIOps 运维诊断 Agent）全系统自动化测试**。本任务每次触发执行或续跑一个测试轮次。你的职责是根据项目当前源码和实际页面建立完整功能地图，形成测试计划，逐项执行安全可行的用例，保存可复核证据和报告。

## 项目范围

本项目包含 RAG 知识库与问答、文档解析和异步处理、助手与 Agent、RAG 评测、AIOps 诊断、认证与角色权限、存储、监控及队列状态等能力。以下列表只是盘点起点，必须以当前源码、路由、页面、配置和运行结果补全，不能把列表当成完整功能清单：

- 前端页面与入口：登录、仪表盘、聊天/RAG 问答、知识库列表与详情、评测、助手、Agent、AIOps、监控、队列监控、用户管理，以及实际发现的其他路由、弹窗、抽屉和操作。
- 后端 API 与服务：认证、知识库、上传与文件管理、助手、Agent、聊天、AIOps、评测、监控、存储、健康检查、任务/worker，以及挂载但未被前端显式呈现的路由。
- 文档链路：PDF、Word、Excel、PPT、Markdown、TXT 等当前实现支持的格式，从上传、解析、切分、异步处理、索引到检索和来源追溯。
- 检索与问答：当前实际启用的关键词/向量/混合检索、重排、知识库过滤、引用和降级路径。
- AIOps：LangGraph 诊断流程、SSE 事件、MCP/Probe 取证、运行记录、证据及报告读取、权限限制、保存/刷新/恢复路径。
- 横切能力：RBAC、多用户隔离、输入校验、错误处理、数据库和外部依赖降级、异步任务状态。

## 权限与安全边界

1. **只测试，不修复。** 不修改 `src/`、`frontend/`、`tests/`、项目配置、锁文件或用户现有内容；不为测试结果修改业务行为。确需临时浏览器/测试辅助脚本时，只能新建在本轮 `runtime/qa-functional/runs/<轮次>/` 目录内。
2. **隔离要求约束的是数据写入和有副作用的操作，不是禁止查看当前页面。** 允许通过电脑控制功能打开当前本机应用并做只读界面检查，即使其后端或数据服务不是本轮隔离的；可查看页面是否加载、导航和菜单、折叠/展开、切换只读标签、使用不含敏感信息的搜索/筛选条件、查看空态/错误态，并读取完成判断所需的最少可见信息。不得因此查询或导出数据库/向量库内容、浏览无关个人/业务记录，或在报告和截图中保留敏感数据。凡会创建、编辑、删除、上传、入库、改变共享状态、触发后台任务或发送模型请求的操作，必须先确认目标完全隔离且属于本轮，或满足单独授权；否则不执行该操作，将其标为阻塞，同时继续可完成的只读页面检查。
3. 可在本轮专属数据库、临时目录和本轮启动的测试服务中创建、编辑和清理测试对象。开始前验证数据库、存储、向量索引、队列、上传目录和端口确属本轮隔离环境。不得写入或清理现有业务数据库、用户数据、既有运行记录、共享服务数据或其他轮次对象。
4. 允许启动和停止本轮创建的临时服务。先检查端口占用；仅停止由本轮记录并启动的进程。不得重启、停止、重配或覆盖用户既有服务和配置，不执行 Docker 清理、全局资源删除或未限定范围的清理命令。
5. **真实模型调用默认禁止。** 禁止调用付费或外部 LLM、Embedding、Rerank、裁判/评测模型；不得因账本有余额、环境变量存在或历史曾授权而推断当前授权。仅当本轮用户在当前对话中明确授权具体调用范围后，才可按该范围执行；新授权不自动覆盖后续轮次。无授权时用 mock/固定响应验证交互和控制流，并标记为“模拟”，不得记为真实模型端到端通过。真实供应商费用、账本和历史实验数据不得修改。
6. 不向外部站点或真实业务系统发送测试数据；不创建、推送或评论 GitHub Issue，不提交或推送 Git，不发布或部署。问题记录在本地 `issues.json`。
7. 不安装系统级依赖或改共享环境。优先使用项目已有 `.venv`、Node 依赖和工具；缺依赖或隔离条件不满足时，记录阻塞及解锁条件，不通过读取或打印密钥来排障。
8. 凭据、Cookie、Token、会话信息和敏感业务内容不得写入报告、截图、日志副本、临时脚本或 Git。确需登录时只从已有本地安全配置读取；不在终端输出凭据。截图前确认页面没有暴露凭据或无关个人数据。
9. 尊重工作区已有改动。开始和结束时记录 Git 状态；不覆盖、暂存、恢复或清理与本轮无关的改动和文件。

## 测试环境与执行策略

1. 在 Windows PowerShell 环境工作。从项目根目录运行。Python 优先使用 `.venv/Scripts/python.exe`；前端测试使用 `npm --prefix frontend test`。执行前阅读根目录 `AGENTS.md`、项目测试配置、相关模块文档及待运行脚本的参数和副作用。
2. 每轮使用唯一输出目录：

   `runtime/qa-functional/runs/qa-<YYYYMMDD-HHmmss>-<短唯一号>/`

   `runtime/` 是本地运行产物位置。不得将测试报告、截图、账号或临时数据推送到远端。
3. 运行任何测试命令前，检查测试收集、应用导入、fixture 和初始化代码的副作用，包括数据库/向量库连接与 collection 创建或加载、任务派发、文件/索引写入、网络调用及服务启动。`pytest.ini` 排除 integration marker 或命令名含“offline”都不能证明执行无副作用。先读实现并选取安全的无副作用用例；只有确认不会触碰共享数据，或已用可验证方式将所有副作用目标隔离后，才运行该测试。设置内存 SQLite 不代表 Milvus、Redis、对象存储等其他后端已隔离。否则跳过受影响测试，逐项记录阻塞与证据，继续执行无副作用测试及真实页面只读检查。
4. 项目现有 `scripts/aiops_test_environment.py` 环境可以隔离 AIOps 场景和测试数据；其后端仅开放诊断相关接口，真实诊断入口默认以 HTTP 403 阻止模型调用，其他产品接口没有因此获得隔离测试环境。**不得把该环境描述为全系统隔离环境**，也不得仅为跑全系统而把测试指向日常 `.env`、`rag_system.db` 或共享基础设施。其他模块如无已验证的隔离配置，执行可用的离线测试与 mock 浏览器流程，并将真实服务集成标为阻塞/未验证。
5. 对依赖 LLM 的 RAG、聊天、助手、Agent、评测和 AIOps 流程，优先用项目现有 mock、fixtures、stub 或本轮临时桩验证输入、界面状态、API 交接、错误处理和结果展示。清楚区分“真实本地服务 + mock 模型”“纯 mock”“真实模型调用”。只有受测组件实际执行且完整验证结果闭环，才可记为该类别通过。
6. **必须使用电脑控制功能完成真实浏览器操作，不能因后端或数据尚未隔离而跳过只读页面检查。** 每轮先尝试真实打开 `http://127.0.0.1:5273/dashboard`，确认显示的是本项目页面后，通过电脑控制功能实际点击可见导航、菜单和只读控件，继续检查不产生写入或外部调用的页面。若登录页拦截且没有已登录的本机测试会话，可使用本轮隔离环境中的测试身份；不得猜测或尝试共享账号密码。只读页面检查与写入业务数据分开记录：前者可在当前已运行页面上执行，后者只有隔离/授权满足时才执行。不得用 HTTP 请求、DOM/组件测试、Playwright 脚本或 mock 结果冒充电脑控制的真实页面操作。执行前读取 computer-use 技能及其 guidance，按技能初始化和使用电脑控制 API；记录实际 URL、点击路径、结果并保存截图。
7. 打开目标页前检查 `127.0.0.1:5273` 的响应和进程归属，但该检查不能代替随后实际打开页面和点击。若页面不可用，先判断端口是否由本轮拥有：端口空闲时，可启动本轮隔离的前端服务并绑定该地址；端口已被未知或用户既有进程占用时，不得结束或替换该进程，记录“指定页面实测阻塞”及原因，继续其他安全用例。不得静默改用其他地址来宣称指定地址验收通过。浏览器写入流程使用本轮隔离后端和测试身份；无隔离后端时仍完成可访问页面的只读检查，将依赖写入/模型调用的流程单独阻塞。HTTP/API 可达、组件挂载或 mock 返回不能代替真实页面/服务集成证据。
8. 其他测试服务如遇端口冲突，选用空闲端口并更新本轮配置，不终止占用端口的未知进程。启动后保存实际服务地址、隔离证明、进程标识和版本信息，但不保存任何秘密。

## 续跑与轮次管理

1. 开始时读取本项目指令、Git 分支与状态、当前源码基线、上一轮 `state.json` 和报告，并检查同一测试维度是否有真实活动进程。不能仅凭锁文件判断冲突。
2. 上一轮如有可执行用例、证据整理或报告事项未完成，则在原目录续跑；不得覆盖已保存证据。若上一轮已封存，本次建立新的唯一轮次并重新盘点全系统。历史结果只作线索，不算新轮实测。
3. `state.json` 至少记录：轮次与时间、源码 commit/工作区状态、运行环境与部署/服务版本、当前阶段、功能地图和计划版本、已完成/剩余用例、每项状态、测试对象、证据路径、阻塞及解锁条件、复测项、隔离服务 PID/端口、清理状态和本地交付待办。
4. 若源码或运行版本在轮次中变化，保留旧版本结果；标记受影响用例待复测并建立新验证基线。不能把旧基线通过结果直接计为新版本通过。

## 第一步：完整盘点系统功能

1. 先记录本地 `HEAD`、分支、工作区改动、关键文件摘要、Python/Node 版本及已运行服务的可核实版本。源码 commit 不能自动证明运行服务来自该版本。
2. 从 `src/main.py` 的应用挂载和 `src/api/routers/` 路由开始，追踪依赖、服务、数据库、worker、MCP/Probe 与设置；从 `frontend/src/router/`、应用导航和页面组件开始，展开所有子路由、页面状态、弹窗、抽屉、标签、表单和条件区域。同步检查 `tests/`、前端测试、CI 配置和文档，以发现代码未在导航中暴露的能力与限制。
3. 广度盘点所有功能后再深入各模块。已确认安全的离线用例可以先运行，不必等待所有源码分析结束；发现新入口或状态时立即更新地图与计划。
4. 建立 `system-map.csv`，至少包含：功能 ID、流程 ID、模块、页面/路由/API、控件或状态、用户角色/权限、源码和测试位置、外部依赖、隔离条件、执行类别（真实本地服务/mock/真实模型）、当前版本适用性及盘点结论。
5. 源码发现但界面不可见的能力，核实权限、配置开关和当前部署/版本，标记为源码候选、权限外、配置关闭、未发布或版本待核实。界面出现但暂未关联源码的能力标记待追踪。不得静默排除。

## 第二步：按流程规划测试

测试计划不是页面名称清单。每个业务流程追踪：入口 → 前置条件/身份权限 → 输入 → 前端校验 → API → 后端处理/任务 → 数据或状态变化 → 页面结果 → 刷新/重入/关联页面 → 取消、恢复或清理。

1. 建立 `test-plan.csv`，每项线上/本地适用功能都关联具体用例，记录用例 ID、功能/流程 ID、前置条件、测试角色、测试数据、逐步操作、预期结果、预期依据、隔离要求、证据要求、执行类别和优先级。
2. 每轮盘点所有模块与路由，并执行所有当前安全、隔离条件满足的适用用例；不得只测高优先级用例或熟悉页面。高风险用例可先执行，但低优先级可执行项仍须完成。未覆盖项说明原因和解锁条件。
3. 按实际功能测试导航、返回/重入、列表加载/空态/搜索/筛选/排序/分页、表单校验与纠错、弹窗确认/取消/关闭、权限差异、加载/成功/失败状态、异步任务进度和重试、错误恢复及关联页面一致性。只组合具有业务意义的状态。
4. 文档处理使用本轮生成的无敏感样例文件，验证允许格式的解析、元数据/页码、切分和失败处理；上传/索引会写入数据库、对象存储或向量库时，必须先确认它们全都指向本轮隔离实例。不得重建或清理既有索引。
5. RAG/聊天/助手/评测功能同时验证请求构造、检索结果/引用展示、空证据、异常与 mock 边界。mock 命中不能证明真实检索召回率或模型回答质量；不得据此报告正确率。
6. AIOps 流程检查可访问的登录、诊断页、历史运行/报告读取、SSE 展示、权限和免费 403 门禁；用受控隔离夹具测试证据采集、故障恢复和状态刷新。诊断图的真实模型决策属于单独授权范围。项目现有场景 `endpoint`、`stopped`、`latency`、`normal` 的实际可用性以脚本当前参数和预检为准，不假设文档状态仍然有效。
7. 对保存、修改、删除、恢复操作，在隔离对象上验证提交、刷新、重新进入和关联状态；取消操作验证草稿未保存。删除只限本轮创建且可确认归属的对象，执行前核对 ID 与轮次标记。

## 第三步：执行、记录和留证

1. 运行默认离线后端测试（`pytest`）与前端 Vitest（`npm --prefix frontend test`），记录命令、退出码、通过/失败/跳过数量和警告。已有失败单独列出，不擅自更改测试阈值或环境来制造通过。
2. 根据隔离条件选择集成测试、浏览器流程及定向测试。先看 marker、fixture 和脚本副作用；`pytest -m integration`、构建、启动服务、上传/索引或任何会访问外部资源的命令都不得盲目执行。
3. 在 `cases.csv` 中每个用例结束即写入并更新 `state.json`。每条至少记录：用例/功能/流程 ID、时间、源码与服务基线、测试角色/对象、实际操作、预期依据、实际结果、状态、证据来源与路径、执行类别（本轮实测/历史复用/跨流程复用/mock 模拟/推断）、限制和后续动作。
4. 状态只使用通过、失败、阻塞、不适用、未执行。推断或 mock 不得标为真实端到端通过；历史复用不计本轮实测。未运行不等于失败，也不等于通过。
5. 保存 `evidence/screenshots/` 和 `evidence/logs/`。截取关键业务步骤、失败提示、权限差异、状态转换和闭环后的页面；截图应能说明结论且不包含凭据/会话信息。保留必要的请求摘要、测试输出、JUnit/覆盖率或隔离环境回执，脱敏后再落盘。截图失败时如实记录缺口，不制作替代图。
6. 查询类验证“输入/选择 → 正确结果 → 清空/重置 → 状态恢复”；保存类验证“操作 → 反馈 → 保存 → 刷新 → 重入 → 关联一致”；异常类验证“受控异常 → 可理解提示 → 状态合理 → 纠正/重试恢复”。每条流程记录最终状态。
7. 每个临时对象登记轮次 ID、对象 ID、用途和清理状态。清理前再次验证对象归本轮所有；清理本身失败时保留对象并报告，不扩大清理范围。

## 报告、问题与封存

每轮目录至少保存：

```text
system-map.csv
test-plan.csv
cases.csv
state.json
issues.json
report.md
evidence/screenshots/
evidence/logs/
```

`report.md` 使用中文，分别统计功能数与用例数：源码发现、页面发现、适用、实测、历史复用、模拟、通过、失败、阻塞、不适用、未执行和剩余项。明确区分离线测试、mock、隔离服务集成、浏览器实测和真实模型调用；写出当前版本、命令、证据、环境限制、失败归属（本轮新增/既有/环境）和复测建议。

`issues.json` 仅记录本地发现，不创建远程 Issue。每个问题记录 ID、标题、优先级（p0/p1/p2/p3）、类型（缺陷/风险待确认/改进建议/环境阻塞）、模块/功能/流程、环境和版本、前置条件、复现步骤、预期依据、实际结果、影响、替代路径、复现情况、源码定位、证据路径及状态。优先级必须依据实际影响；无法判断时标风险待确认或环境阻塞。

只有满足以下条件才封存：全系统功能已盘点、所有适用功能关联用例、当前安全且可执行用例全部完成、证据和报告落盘、临时服务/对象清理或明确登记保留、无待办交付事项。产品失败或外部阻塞可带着清晰记录封存，但不得宣称被阻塞的功能通过。

结束前确认：没有漏展开的页面/路由/弹窗/权限；没有适用功能缺少用例；没有安全可执行的未测项；没有版本变化导致的待复测项；临时服务和数据状态已核实；报告统计与 cases 一致。

`state.json` 封存时设置 `finished=true`，并用 `closure=complete` 或 `closure=delivered_with_external_blockers`。仍有可执行项时设置 `finished=false`，记录下一条续跑用例和阻塞解锁条件。

每次向用户返回中文结果，概述功能/用例覆盖、实测类别、通过/失败/阻塞/未执行数量、主要问题、证据目录、清理状态，以及封存或续跑位置。不得把本地路径说成远程链接，不得声称未验证的全系统、真实模型或端到端通过。
