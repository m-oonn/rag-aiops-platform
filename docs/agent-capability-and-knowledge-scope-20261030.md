## 1. 配置文件读取计划

真实失败场初始计划提出“打开配置文件，找到 localapp”，但本场 Probe 只有已登记的服务、日志、进程、端口等只读工具，没有任意配置文件读取接口。自由文本 `Plan.steps` 原来只通过字符串类型校验，不能保证计划可执行。

- `planner.py` 提示词明确能力边界，并使用 `tools.py` 的共享检查识别显式中文/英文配置文件读取。初始计划中识别出的不可执行步骤，仅在 `probe_text_log` 已加载时替换为中性的应用日志核对；否则删除该步骤，不虚构其他采集能力。
- `investigation_reference_context` 留下“文件读取未执行、原配置内容未核实”，供执行器和后续调查器读取；这只是能力限制，不进入现场证据。
- `executor.py` 在发送模型请求前再检查一次，覆盖旧计划和后续重规划。无法执行时返回 `tool_execution / plan_validation / unavailable / unsupported_config_file_read`，不调用工具、不伪造配置原文或 Probe 观测。
- 已加载的终端输入与提交工具保留既有审批路径，未扩大其命令权限。

边界：该规则识别已覆盖的显式配置文件读取表达，不是任意自然语言能力的完备判定器。正常的“检查配置解析错误日志”仍可执行；真正的文件、服务和对象权限继续由实际工具及白名单控制。日志核对不能证明原配置内容。

## 2. 知识库范围沿实际调用生效

上次场次查询 `kb_id=1/0`，控制器夹具库实际为 14；这是调用范围错误，不能据空结果宣称目标知识库无资料。

- `scope_knowledge_tools` 保留原工具 schema 的其他字段，只为 `search_knowledge_base.kb_id` 加上实际范围的枚举。
- 单库允许省略 ID，并在执行前填入唯一真实 ID；多库必须显式选择。显式错误 ID、布尔值、字符串或浮点值不自动改成另一库，直接拒绝，MCP 不会收到该请求。
- 生产加载使用 `EXPERIENCE_KB_IDS`；未配置时维持原行为。显式配置无效或工具缺必要 schema 时关闭知识搜索并返回加载错误，其他现场工具保留。此范围是配置约束，不替代知识库服务自身的用户授权。
- 评测加载及实际 `run_model` 均接入限制，控制器现有夹具使用 14；免费自定义知识预检继续支持其指定库，如生产 BM25 库 15。没有把 14 写成全局固定值。
- 工具追踪写入实际默认 ID；`evaluation-record.config.knowledge_kb_ids` 记录运行范围。`audit_evaluation` 核对成功调用与当次请求中工具 schema 的范围；错误调用仍保留失败轨迹，不能计作有效检索。
- 旧记录没有新增字段时只读兼容，不回写旧报告、账本、人工表或实验成绩。新记录参与四组比较时，该范围属于各组必须一致的配置。

真实 PDF/内存 SQL 回归验证：限制在隔离库 901 时拒绝 0/1/902，省略 ID 可以检索到原 PDF 第 2 页及来源；在线向量和重排构造器保持禁止。固定调用和离线四组接线不等于真实模型已学会正确检索。

## 3. 嵌套结构失败诊断

共享 `ainvoke_structured` 的日志区分 `function_calling` 与 `json_fallback`，只记录 schema 名称、异常类型、受控字段路径及错误码。

本轮进一步修复两个先复现的漏洞：

1. 全局收集字段名会把恰好同名的动态字典键误当成 schema 字段。现在按当前位置遍历 schema，解析 `$ref`、可选分支、数组项与字典值；动态键位置始终脱敏，数组下标受限。
2. 原来安全异常通过 `from exc` 连接原异常，普通 traceback 仍可带出 JSON 解析错误中的响应正文。现在抑制该异常链，错误阶段及字段信息在安全日志中独立保存。

没有放宽 Pydantic 模型、修改结论门槛、增加模型重试或修复未知的 GLM 返回字段。schema 失败仍按既有失败契约收束。
