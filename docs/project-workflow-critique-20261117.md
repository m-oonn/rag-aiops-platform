# 项目流程梳理与批判

日期：2026-11-17

## 结论

项目已经有一套可审计的诊断骨架：目标解析、白名单工具、证据哈希、工具调用账本、候选原因和引用门槛、保守停止语义、离线回放都已经存在。真正的短板不在 LangGraph 节点数量，也不在预算本身，而在几个跨入口交接没有共用同一套身份、状态和可见性契约。

当前不能把项目描述成“已经具备自主找根因和持续运维能力”。更准确的说法是：有人触发的诊断已有取证和审计基础；持续监察已有事件检测基础；从监察事件到可复查、可继续、可复用的自主闭环尚未闭合。

本报告审查通用调查和持续监察的交接，不重新裁决此前 mall 已通过的具体场次。已登记服务的原因合同可以确认有限原因；这些能力应保留，但不能直接外推到未知项目或 DSH 卡顿。

本轮只做源码梳理、定向免费验证和记录，没有调用真实模型、没有使用预算、没有修改业务逻辑。

## 我采用的检查流程

按一次真实排障应走的顺序检查：

1. 确认现场：故障信号是否来自真实运行路径，时间窗和目标是否明确。
2. 锁定目标：业务目录、Probe 白名单和实际消费者是否一致。
3. 取证：工具是否先登记再执行，结果是否带来源、时间、哈希和权限边界。
4. 鉴别检查：每个检查是否能区分候选原因，失败后是否有合法替代检查。
5. 执行和记录：提议参数、实际参数、拒绝、错误、结果和耗时是否可复查。
6. 更新判断：新证据是否进入候选、引用和下一步，而不是只追加日志。
7. 复核和恢复：结束、失败、等待人工、恢复是否被区分，系统运行是否能被管理员接管。
8. 经验复用：结果是否经过审核后进入下一次可检索的经验，而不是只生成一次性报告。

主要源码读取、复现及测试命令按批保存参数和平台返回，见[过程记录](../runtime/project-workflow-critique-20261117/README.md)。原始失败和输出截断也保留；这是工具已返回内容的记录，不代表绕过工具截断恢复了未返回全文。

## 已经做对的部分

证据边界是项目最强的部分。registered_causes.py 把原因码绑定到已经通过新鲜度、目标、哈希和业务范围校验的记录；规划阶段把知识库内容标为参考，不把 RAG 结果冒充现场事实；read_run_evidence 只允许按 evidence_id 读取受限原文，不接受任意文件路径。这些边界应继续保留。

工具账本的执行顺序基本正确。start_tool_call 在实际调用前登记，finish_tool_call 记录状态、错误、结果和耗时；结果落库失败会重试，仍失败就中止诊断。相比“模型说调用过什么”，这条链能回答“实际调用了什么”。

停止语义比较诚实。调查策略会区分“已定位故障层”和“已确认直接原因”，停止理由会写明“系统没有独立证明其余检查已穷尽”。这比为了完成报告强行填一个根因更可靠。

回放和测试基础是可复用资产。distil_recorded_rounds.py / replay_recorded_rounds.py 把真实轮次中决策读取的状态抽成可提交语料，可在没有本机 runtime 的环境重放。这能防止新改动让已经通过的轮次退化，但它证明的是决策逻辑回归，不是一次新的现场诊断。

## 关键问题

### 1. 监察身份无法读取本轮已保存证据（高优先级）

调用链是：

- continuous_monitor.py:320-325 自动诊断调用 execute(... user_id=None, persist_run=True)。
- planner.py:326-327 和 executor.py:159-161 只有 user_id 非空时才挂载 read_run_evidence。
- evidence_reader.py:40-44 明确拒绝空身份。

因此，监察触发的诊断可以继续发起新的 Probe 查询，却不能按证据编号重新读取本轮已经保存的原文。发生“先采样、后发现需要看完整日志”的故障时，自动诊断会缺少人工诊断可以使用的回读能力。这是流程闭环中的真实断点，不是模型能力问题。

最小改法是明确系统调用的主体与授权，优先复用既有账号和运行授权机制，让受控系统运行能够读取自己的证据；是否需要新增字段，应在实施时按现有模型选择。对外 API 仍按所有者或明确的管理员权限访问，不能仅移除空身份校验。验收必须包含：监察创建的运行能读自己的证据；不能读别的事件或别的目标；读取仍做路径、目标、时间和哈希校验。

本轮隔离工具传输后复现：同样的运行状态，普通用户会附加 read_run_evidence，系统身份不会附加；直接用空身份读取也被拒绝。这不表示系统所有 Probe 工具都为空。完整复现共 6 组契约检查，见[复现结果](/D:/ragPdfSystem++agent/runtime/project-workflow-critique-20261117/contract-reproduction.result.json)。

### 2. “等待人工”会被监察器记成“失败”（高优先级）

continuous_monitor.py:318 默认把状态设为 failed，只处理 complete 和 error 两类事件。启用报告人工审核后，若诊断返回 pending_review，循环结束仍会保存为 failed，事故记录中的报告为空，线程编号却已经保存；原图中的草稿不等于被删除。当前监察显式 terminal_enabled=False，不能据此宣称现场出现过终端审批等待。

这会混淆两种不同的情况：

- 诊断真的失败；
- 诊断停在等待报告人工审核。

最小改法是映射已有图状态，保存 pending_review 和对应线程/草稿，允许管理员按已有审核流程继续；只有实际失败才记 failed。完成审核后还要把结果同步回同一事故。终端审批如果将来开放给监察，再单独处理其状态与权限，不提前增加无用状态。

合成事件已复现：pending_review 被保存成 failed，事故 diagnosis_report 为空。本轮没有启动启用 HITL 的真实模型监察，这属于确定的条件分支缺陷。

### 3. 系统运行记录与管理员复查入口没有接上（高优先级）

普通诊断通过 aiops.py:_owned_run 按 run.user_id == current_user.id 控制访问。监察运行的 user_id 是空值，所以即使管理员知道 diagnosis_thread_id，也不能通过普通的 /aiops/runs/{thread_id}、steps、evidence 或 tool-calls 入口查看这次系统运行；监察接口目前只返回事件证据和最终报告。

结果是：后台能生成报告，但管理员不能沿同一条运行记录复查它为什么做了哪些检查、哪些检查被拒、哪条证据改变了判断。这与项目强调的“每一步工具记录”不一致。

修复方向是增加管理员专用的 system-run 查询投影，或把 incident 与 run 建立受控关联；不能简单把 user_id=None 当成所有人可读。

### 4. 正式 Diagnosis 页面没有展示工具调用账本（中高优先级）

后端已有 /aiops/runs/{thread_id}/tool-calls，但 frontend/src/views/Diagnosis.vue:245-260 只并行读取 evidence 和 steps，没有读取 tool-calls。

用户在页面上能看到证据和步骤，却看不到：

- 实际调用了哪个工具；
- 提议参数和实际参数是否不同；
- 调用是成功、拒绝、超时还是不可用；
- 结果是否被截断；
- 失败后为什么换路。

这会让最有价值的调查资产停留在数据库里。应在现有诊断视图增加一个调用时间线，显示脱敏参数、状态、拒绝理由、耗时、结果摘要、结果截断标记和关联证据；读取失败应显示错误，不显示“没有调用”。

### 5. 步快照是摘要，读取失败却伪装成空列表（中高优先级）

graph.py:82-98 的执行器快照只保存最近一步结果的前 200 个字符；这适合页面概览，不足以回放完整决策。完整工具结果虽然另有账本，但步骤快照没有保存本步骤对应的调用 ID、证据 ID、下一步理由和状态变更。

更严重的是 run_store.py:175-203 查询步快照遇到数据库异常时返回 []。页面会把“查询失败”看成“没有快照”，管理员无法判断记录缺失还是诊断本来没有步骤。

建议保留摘要，先把已有调用 ID、证据 ID 和决策记录关联到步骤；不必为此复制完整 checkpoint 或新建另一套事件系统。读取异常改为显式错误或 503。工具账本已经采用显式 ToolCallAuditReadError，步快照应保持同一语义。

记录本身还有两层边界：工具账本结果最多保留 64000 字符，超限会标记截断；Probe 原文可以另有证据文件，但不能推断所有非 Probe 长结果都有完整归档。规划前的 _retrieve_experience 是内部直接调用，也不能因为 MCP 调用有账本，就称每一种底层检索 I/O 都有相同审计记录。应先给长结果补受限原文引用，给内部检索补查询范围、来源、失败/空结果和耗时，而不是一律扩大上下文。

### 6. RAG 有读取和离线回放，但没有被证明形成生产经验闭环（中优先级）

当前能确认的是：

- planner.py:147-216 按显式知识库范围检索经验，并明确标为参考；
- local_retrieval.py 和本地 runbook 能提供降级读取；
- distil_recorded_rounds.py 生成的是测试回放语料，不是生产经验发布。

本轮没有找到“诊断结果自动生成经验候选 → 人工审核 → 发布到经验库 → 下一次检索可引用”的生产链路。因此，项目目前是“经验可被读取、历史结果可被回放”，还不是“经验自动沉淀并持续提高下一轮诊断”。

最小闭环应包括：候选经验、来源运行、证据引用、适用范围、限制、审核状态、发布版本和撤回记录。未经审核的失败结论不能直接进入可检索知识库。

### 7. 监察信号覆盖很窄，不能代表持续运维能力（能力缺口）

continuous_monitor.py 当前只消费 Prometheus up：

- 连续 3 个新鲜失败样本开事件；
- 连续 2 个新鲜正常样本关事件；
- 过期、缺失和错误样本为 unknown。

这套规则适合作为 Prometheus 抓取失败触发器：up=0 可能来自进程、网络、采集路径或认证等原因，不能直接说业务服务已停止；两次 up=1 也只能证明抓取恢复。它不直接覆盖业务延迟、错误率、桌面 UI 卡顿、插件 JavaScript 异常或事件循环阻塞。告警关闭与业务功能恢复应分别表达，后者还需真实业务请求验证。

扩展时应先增加可审计信号源和时间窗，再增加诊断策略；单纯增加图节点不会产生这些现场证据。

### 8. 计划、策略和图执行限制必须分别解释

代码中同时存在：

- planner.py:41 计划硬截断为 6 步；
- dynamic_classification.py 的 _MAX_STEPS = 12；
- default.py 的 MAX_STEPS = 8；
- sidebar 分支每支最多 2 步。

6 步控制初始计划长度，不是整个自主调查只能查 6 次。dynamic_classification.py:708 和 default.py:197 的固定步数停止条件都排除了 autonomous_investigation；不能把 6、12、8、2 相加成一个总限额。图还有库自身的运行约束，本轮未证明这些约束导致过哪一场历史失败。预算不足或未知用量也确实可以阻断请求，必须逐场按账本和 stop_reason 判定。

本次确认的身份、状态和审计交接问题，增加节点或预算都不能直接修复。过去日志已经指出的谓词缺口也必须先有真实证据源，不能用更长循环补出来。项目应把计划截断、图运行错误、无进展、证据不足、费用守卫分别记录。

验收时应要求每个停止记录同时给出：已执行调用数、尚未验证的候选、可用但未执行的检查、阻断原因和是否可以人工继续。

### 维护风险：调查主模块职责集中

当前 investigation.py 为 4522 行、303048 字节。长度本身不是缺陷；关键是同一模块同时承担上下文压缩、候选记忆、具体查询生成、守卫协调、原因谓词、引用审核、停止判断和报告拼装。身份、证据新鲜度或工具契约改动，容易同时影响取证、计划和报告。

这反映了长期围绕具体失败补分支的成本。应先把上述跨入口缺陷补上最小回归，再在需要修改的边界复用已有 probe_checks、registered_causes 和报告模块；逐步让“证据是否合法”“下一项检查能否执行”“能否发布原因”使用一致接口。不建议为清理文件长度重写整张图，也不建议把八个逻辑阶段机械拆成八个 LangGraph 节点。

确定性原因合同是一项设计取舍：已登记故障能严格核验，未知故障只能保留假设或故障层定位。新增一种能力应先证明所需事实确实能采到、能区分竞争解释，再增加原因合同；验收必须含相似但原因不同、证据缺失、过期和未知故障，避免只在熟悉夹具上表现良好。

### 文档与证据漂移

docs/continuous-monitor.md:39 仍保留早期 getTabs 模拟、未找到现场栈及未修改插件的描述；后续 DSH 记录已保存 teamMembersOf 的现场栈和数组防护修改。这些阶段应标明时间和后续入口。完整成员功能恢复与卡顿归因仍没有证明，不能因为修正旧文档就补写成功结论。本轮只登记这一冲突，未覆盖原文或修改 DSH。

## 建议顺序

1. 先修身份和状态契约：系统运行可安全读取自己的证据；pending_* 不再写成 failed；管理员可从事件进入对应 run。
2. 再把账本接到正式页面：工具调用、步骤、证据、报告使用同一 run_id，读取错误显式显示。
3. 再补快照关联和失败语义：步骤保存调用/证据指针和哈希，查询失败不返回空数组。
4. 再补 DSH 现场适配器：插件栈、宿主/插件版本、事件循环延迟、性能窗口和时间窗日志进入真实 Probe/采集链。
5. 最后做经验发布闭环：只发布有证据、有范围、有审核记录的经验，并用下一轮真实或隔离验收证明它被检索和正确引用。

每一步都应有“初次失败 → 修复 → 同一输入重跑 → 恢复/清理”的记录。预算只控制真实模型请求，不应承担状态机、权限和证据契约的职责。
