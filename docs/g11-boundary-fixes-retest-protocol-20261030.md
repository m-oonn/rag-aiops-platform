## 4. 后续获单独授权后的流程与停止条件

1. 再核对准备包、最新账本和授权范围；发现其他运行已产生新账本时停止，更新起点与累计 cap，不能继续使用旧前缀。准备检查仅证明指定链完整，不能自动发现其他目录的新消费。
2. 控制器使用独立动态端口、进程、数据库、thread、证据目录及 runbook 夹具。正常/故障预检失败不得进入模型；每场重置前记录带时区 `observation_not_before`，禁用共享 `probe_list_evidence`。不接管常驻服务。
3. 模型只接收中性症状和允许对象。先核对原始 Plan、实际执行计划及能力限制记录；显式配置文件读取应改查允许日志或在执行前拒绝，不把日志说成配置原文。该规则只覆盖已识别的显式表达，不是任意自然语言判定器。
4. 若发生知识查询，实际 schema 的 `kb_id` enum、工具轨迹和 `evaluation-record.config.knowledge_kb_ids` 均须为 14；省略时填 14，显式错误值在 MCP 前拒绝。没有知识调用则记未覆盖，不能据此声称该项实测通过。
5. Plan/InvestigationDecision 应通过现有校验；若两种格式均失败，保存 schema、阶段、安全字段路径、错误码与异常类型，按失败契约结束，不保存模型正文或值、不放宽校验或加重试。HTTP/鉴权等不可恢复错误亦停止。
6. 若取得本场有效依赖失败证据，核对 `model_suggestion`、`policy_selected_check` 与实际工具调用：依赖探测 → 本轮依赖端口监听 → `service='downstream'` 映射进程 → 允许的独立日志。端口及路径取本轮配置，不固定历史 6299。
7. 报告逐项说明已核实事实、未执行检查及原因、真实工具/权限/采集阻碍。无监听或无进程不证明崩溃原因；日志不能解释退出原因时如实未决。仍有可行鉴别检查时继续，不用“模型没提出检查”冒充不可查。共享补查规则不计为保护或矛盾创新行为。
8. 累计达到 47、usage 缺失、调查失败、隔离或记录门槛失败即停止，不另起场、不换模型、不提高 cap。格式 fallback 可在场内发生，不能承诺每次可恢复格式错误都立即停止。保留失败后恢复专用业务并独立核对，逐个清理本轮所属进程/端口；清理失败明确报告。

先判断流程是否完成，再分别判断定位、引用支持、建议适用性与机制机会/动作。没有反证机会就保留未覆盖，不强制触发。`localized_fault` 或诚实 `unlocated` 不自动等于诊断正确；无 complete 的失败报告不算流程完成。
