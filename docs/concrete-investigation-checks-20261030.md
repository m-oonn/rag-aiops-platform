# 具体检查参数与结果消费（2026-10-30）

本轮把后续 Probe 检查的决策与执行接通：调查器提出问题、工具和具体参数，执行器通过原有范围守卫后直接调用，再将现场返回和执行记录交回调查器。具体检查不再额外调用执行器模型来选择参数和生成总结。初始计划、非 Probe 检查和旧 checkpoint 保留原执行路径。

## 解决的问题

上轮仅修复候选契约和第三次精确重复查询。原 G11 的 14 次工具调用没有第三次精确重复，因此那项修复并不能节省原场请求。进一步追踪发现：调查器选择检查后，执行器仍用模型重新选择参数，再用一次模型总结；目标可能偏移，且每次检查都增加请求。

这轮直接修改该调用链，没有重跑付费场次，也没有给原失败场补写报告或成绩。

## 实现与调用者

- `strategies/investigation.py`：决策与候选检查增加 `next_arguments`、`repeat_reason` 和 `repeat_evidence_ids`。新模型提出的 Probe 检查必须有工具到参数的映射，无参数工具填空对象；原始模型提议保持原样。引用别名转成真实证据账本 ID，候选保护、矛盾改向与后续检查继承具体参数。
- `probe_checks.py`：复用查询归一化，核对参数类型、默认值、上限、允许对象及最新有效 inventory；拒绝进程应用的 Windows 服务查询、未配置事件通道和未允许日志路径。根据同一具体查询的返回与执行失败生成 `check_progress`，区分未执行、已观测、部分结果、不可用和不适用。
- `executor.py`：具体 Probe 检查直接执行，仍经过业务范围、配置能力、重复判断及返回证据校验。记录实际参数、计划参数、问题、复核理由、证据关联、状态与耗时；参数偏移被拒绝。原始返回进入账本和下一轮决策，执行状态不冒充根因结论。
- `events.py`：SSE 摘要附带具体计划和检查进度，继续脱敏并过滤未验证因果文字；刷新读取复用 checkpoint。未增加前端展示组件。
- `scripts/mechanism_behavior.py`：实际查询参数必须与候选计划一致，才计为机制检查执行；默认参数按归一化比较。旧轨迹字段缺失保留兼容。
- 更新免费机制验收脚本和既有 API/SSE/刷新、真实 PDF 消费等测试调用方，提供明确参数并核对减少后的模型调用次数，没有放宽生产契约。

## 结果怎样约束下一步

1. 同对象同参数已有结果，先消费结果。再采样必须说明复核目的，并关联该查询的有效证据；虚构 ID 不放行。
2. 最近两次同参数有效观测诊断内容相同，仍拒绝第三次，复核理由不能绕过。不同对象、日志路径、行数或窗口继续分别判断。
3. 同一具体查询上次失败或被拒绝，即使没有生成 Probe 观测也保留限制，不换个检查名称原样自动重试。
4. 主检查只是重复，而当前关键候选还有合法、未执行的鉴别检查时，转去执行该检查。保护与矛盾开关仍只控制各自机制，四组共用上述能力。
5. 不能继续时保存证据、未决问题和实际阻碍；模型没有提出检查不等于工具穷尽，故障层定位不等于根因确认。已有模型超时或预算拒绝出口继续保留未完成报告。

复核理由只证明模型声明了目的，程序不能验证所有跨对象检查的语义鉴别力。新增契约可能使缺参数的模型提议较早停止；这是可观察的失败，不能据此宣称真实模型已兼容。
