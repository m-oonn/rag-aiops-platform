## 修了什么

| 问题 | 实际修改 | 可观察结果 |
|---|---|---|
| 编排窗口 | `CompetingFaultFixture.reset()` 在旧日志清空后、启动和注入前记录并返回时间；免费场景调用者统一消费返回值，不放宽采集守卫 | 本轮 localapp 日志可经执行器、MCP、Probe 接收；旧轮次证据及旧日志行仍拒绝 |
| 知识基线 | 本地 runbook 新增独立基线模式，核对 Markdown/JSONL 文件哈希、本地检索实现及实际 top-k；评测入口在模型创建前要求 manifest 并校验，结束后再次核验 | 任意本地材料不必伪装成固定 MCP fixture；增删改、manifest 和实现基线篡改均拒绝，审核读取方消费同一基线；原 MCP 模式回归通过 |
| 停止审计 | 快照保存当轮有效观测历史及摘要校验值；审计按记录时刻校验历史、元信息、当前证据视图，并核对执行记录，再用原守卫重建 | 原场第 8 步的选择、两个重复拒绝理由能一致重建；历史、对象、执行记录篡改会失败；必要历史缺失的旧记录为 not_assessed |
| 候选消费 | 已有检查进度补充实际返回内容、预期及剩余未知；下一次已有决策请求前重新投影最新有效结果和有限条件关系 | 新监听证据在请求前已反驳“无监听”；不再把上轮 neutral/unexecuted 当作当前进度；空日志不能证明进程不存在，改名不能绕过同参数重复守卫 |
| 报告收束 | 从同一份已验证 `diagnosis` 生成主报告，顺序为对象影响、事实引用、支持解释、处理复测、未知与停止；候选和详细拒绝留在现有详情字段 | 配置字段与报错关系保留；下游报告保留配置身份/采样覆盖限制、日志来源边界及未核验检查；关闭服务重读一致 |

知识基线是第 1 点必须关联的生产与消费路径，并非新增服务。当前隔离本地检索实际使用现有关键词检索；没有把它描述成向量检索或新增 BM25 服务。JSONL 也会被该检索器读取，因此一并纳入本地完整性记录。新增字段仅在评测快照、基线产物和既有调查记忆中；公开端点、有限条件类型及服务结构未改变。

## 边界与后续

本阶段没有通用因果语义识别：只有显式合法的有限条件按现场证据更新，纯因果解释继续未知。配置身份进程未找到不能扩大为所有相关进程不存在；空日志不能判定未启动或崩溃。报告压缩没有增加现场证据，也没有让原场不可读的日志变成已核验事实。
