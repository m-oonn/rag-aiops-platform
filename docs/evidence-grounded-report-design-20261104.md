# 证据约束的报告模块：技术调研与确定方案

实施更新见[离线交付记录](evidence-grounded-report-closeout-20261104.md)。以下保留设计时点的判断和限制，不将其改写为真实模型验收结论。

2026-11-04。交付性质：公开技术调研、当前调用链核对与设计；尚未实现，不新增模型、现场观测或付费调用，不改历史报告与审核结论。

## 1. 决定

在现有 Python 后端增加一个内部报告模块 `src/agent/aiops/reporting.py`，采用“确定性证据整理 → 一次受限模型编排 → 程序校验 → 确定性渲染”。复用当前模型工厂、Pydantic、预算账本、检查点和报告事件，不部署新服务、不增加依赖或公开 API。

模型负责从允许的对象、事实、解释和建议中选择、排序、合并展示；事实数值、证据引用、结论等级、操作前提、未知与停止理由由程序保留。模型编排不可用时，用同一结构生成规则报告。这个模块整理已有调查结果，不执行补查，也不靠润色补出根因。

本轮最需要解决的是“该优先处理谁、哪些对象只是观察到异常、什么还不知道”，而不只是固定五个标题。候选结果投影中的 inventory/resources 空摘要属于更早的调查输入问题，单独保留，不能声称报告模块解决了重复检查。

## 2. 市面技术怎样处理，以及适用边界

下表根据官方公开文档核对产品行为，不据此推断厂商未公开的内部实现。资料截至本次查阅；产品能力和型号支持可能变化。

| 技术或产品 | 官方资料确认的思路 | 本项目采用什么 | 不作什么推断 |
|---|---|---|---|
| Datadog Bits AI SRE [S1] | 调查展示摘要、结论和证据；结论可以是找到根因，也可以是证据不足的 inconclusive | 报告保留“未定论”和未完成检查，先解释证据及边界 | 不因生成了报告就宣布找到根因；不采购或复制整套调查产品 |
| Dynatrace Problems [S2] | 区分根因实体、受影响实体和影响，并结合依赖关系呈现 | 分开“优先处理对象”“异常/受影响对象”；使用已有显式对象映射 | 配置依赖关系本身不证明本次传播因果；不引入拓扑数据库或通用因果引擎 |
| PagerDuty AI-generated PIR [S3] | 使用事件资料生成事后复盘草稿，并支持人工审阅、补充和迭代 | 将自动整理结果与人工语义判断分开 | 事后复盘与本项目现场处置报告用途不同；不照搬其复盘模板作为在线诊断正确性的证明 |
| OpenAI Structured Outputs [S4] | 支持的模型和接口可约束 JSON Schema；官方同时明确结构正确仍可能内容出错 | 使用 schema 和本地验证，区分格式约束与事实判断 | 不迁移模型，也不把 OpenAI 的 strict 保证套到其他兼容接口 |
| 阿里云百炼结构化输出 [S5] | JSON Object 保证合法 JSON，但不保证遵循具体 schema；文档明确将 `deepseek-v4.1-flash-1017` 列在 JSON Object 模式，JSON Schema 支持名单则为部分 Qwen 型号 | 沿用当前已使用的 function calling，结果仍由本地 Pydantic 和业务守卫检验 | 不把 JSON Object 支持等同于 strict JSON Schema 支持；具体报告 schema 尚未在当前链路实测，不为本次设计切换模型 |
| Anthropic Citations [S6] | 原生引用可定位文档片段；当前文档说明 citations 与严格结构化输出不能同时启用 | 借鉴可定位原文的引用链，继续使用现有证据 ID 与原文片段 | 不认为“有合法引用”自动证明引用支持因果解释；不新增供应商或原生引用依赖 |

选择组合式方案的理由：本项目已有采集、证据验证和调查状态。再增加一名自主 Agent 或“生成—模型审核—模型重写”循环，会增加费用与失败路径，仍不能独立保证语义正确。固定步骤的报告模块能把当前错误落在明确的输入、编排、校验和渲染边界上。

## 4. 数据怎样进入报告

### 4.1 程序构造证据包

只读取本次有效范围内的证据、已有经过守卫的诊断结果和配置映射；不读取隐藏故障答案，不把控制器记录或模型原始猜测当现场证据。

- 对象：target/service/dependency/port 的现有身份，以及有明确来源的映射。没有映射时保留为独立对象，不按名字猜归属。
- 事实：局部稳定 fact ID、原 evidence ID、对象、采集时间、实际值、采集覆盖和原文位置。ID 只在本份证据包内使用，不创造新证据源。
- 解释：已有有限条件的关系、支持和反对证据、仍未验证的因果解释。保持 observed/supported/unknown 等认知边界；不新增通用自然语言因果裁判。
- 检查：已经完成、失败、不可用、取消的具体检查及原因。已经读过日志，不再生成无具体缺口的“去读日志”。处理前重新采样则明确说明现场可能变化。
- 处置：从已有建议模板构造合法行动选项，保留适用对象、证据、前提、风险和复测。模型不能发明重启命令、配置值或操作权限。
- 必须保留：原 diagnosis kind、流程失败状态、未决问题、证据冲突、关键限制、stop_reason 和人审状态。

按对象、操作和证据 ID 去重；完整原始证据仍保留在原记录。日志和知识材料作为数据处理，不能成为改写状态、执行工具或扩大权限的指令。

### 4.2 程序先划定处置边界

“优先处理对象”是处置优先级，不等于已经证明的根因。第一版仅使用当前可验证关系：

1. 配置快照与同源解析错误相符：生成对应配置对象的修正候选，保留字段和异常。
2. 同一已配置对象出现 TCP 失败、对应端口无监听、配置身份进程未观察到：生成该对象的恢复候选，保留采样和枚举限制，不能写“已崩溃”。
3. 上游仅有 HTTP 失败：保留异常对象；有显式依赖和相符日志时，可以写“与依赖失败相符”，不能自动确认传播因果或排除自身另有故障。
4. 存在多个独立故障、映射不足或冲突时，允许多个处理候选或“优先级未定”，不能强选唯一根因。HTTP 503 不是一律降级成受影响对象。

在本场中，可优先建议核实并恢复 downstream；localapp/edge 的异常保留，安排恢复后逐段复测。若 503 持续，再依据新的具体错误调查对应对象。不能把它们无条件改判健康，也不能删除其异常证据。

### 4.3 模型输出编排方案，不重新写现场事实

第一版输出一个小型 Pydantic 对象，表达：允许对象中的优先顺序、展示的事实 ID、允许解释 ID、行动 ID 及分组。概念结构如下，不是新增公开接口：

```json
{
  "focus_object_ids": ["obj-downstream"],
  "fact_order": ["fact-tcp", "fact-listener", "fact-process"],
  "explanation_ids": ["explanation-downstream-unavailable"],
  "action_order": ["action-restore-downstream", "action-retest-chain"]
}
```

这些 ID 都来自本次证据包；示例不表示提前写给模型的场景答案。受影响对象、必须保留的异常、未知、限制和停止理由由程序补全，不让模型通过遗漏来美化报告。

第一版不接受模型自由创造的事实句、因果结论和操作步骤。可选的解释措辞从经过校验的声明池中选择，由程序插入对象与引用。这会限制语言变化，但能避免把“文字好听”和“证据充足”混为同一门槛。未来如开放自由解释文字，需要另列语义评测，不能宣称现有结构校验已经覆盖。

### 4.4 校验并渲染

本地校验至少覆盖：schema/长度/重复 ID；ID 存在；事实与对象绑定；证据仍属于当前有效范围；处理对象在合法候选内；不能漏掉独立故障、反证或必要复测；不能升级结论等级、抹掉失败或未知；行动满足原前提；不能把完成检查包装成未做建议。

校验通过只表示符合这些规则，不等于证明任意语义正确。模型草案未通过时记录具体拒绝原因，直接使用同一证据包的规则编排，不再让模型自动修一轮。

固定渲染顺序：故障对象与影响 → 关键事实及引用 → 有证据支持的解释 → 人工处理及验证 → 剩余未知与停止理由。主报告不重复展开所有候选和拒绝记录，详情继续保留。规则回退也执行对象区分和建议收束，不能回到当前有缺陷的旧模板。

## 5. 接入、预算与保存

### 接入位置

`InvestigationStrategy.decide()` 给出新的终止结果后，在现有异步 replanner 内调用报告模块，完成后一次返回最终 response、diagnosis 和 investigation_memory。先覆盖自主调查的正常终止；预算停止或调查失败直接使用规则报告，明确未完成，不为美化失败结果追加请求。

不增加 LangGraph 节点、路由、审批点或独立队列。已有 response+diagnosis 的终态直接读原结果，不在刷新或恢复旧记录时补调模型。

报告编排产生同一份最终视图：response 与 diagnosis 中的最终人工建议从该视图生成；原始事实、kind、scope 的既有语义、停止理由和机制记录不被报告器改判。原逐项建议和模型草案保存在内部详情。这样 AIOps 的现有建议详情与主报告一致，无需增加前端页面或公开字段。

### 请求约束

- 使用当前 `create_agent_llm`，不切型号；现有官方瞬态失败兜底政策保留。报告模块也必须进入评测 BudgetTransport 的注入范围和源码签名。
- 最多一次逻辑编排；报告路径关闭格式失败后的第二次 JSON 请求与外层循环重试，SDK 自动重试在该路径显式关闭。通过可选参数或小型局部调用实现，其他调查调用默认行为不变。
- 一次逻辑编排仍可能包括主通道和既有官方兜底的实际 HTTP 请求；逐请求登记供应商、型号、usage、耗时和费用，不能宣传“一份报告必然只有一次 HTTP”。
- 沿用现有单场/累计费用边界、输出上限和超时；报告阶段加不超过现有单请求超时的总等待期限，含兜底，不为报告提高额度。预算不足时发送前拒绝并回退；已发生的用量缺失或费用异常继续按原评测规则失败，不能靠回退掩盖。
- 模型整理失败不抹去已有调查结果；但评测保留报告 degraded/failed，原计划要求遇到请求、计费或记录失败即停时仍然停止后续场次。用户看到可读报告不代表付费验收已通过。

### 持久化与兼容

在既有 investigation_memory 下增加带版本的内部 report 记录：证据包/输入 hash、编排版本、模型解析后草案、校验错误、最终采用 model/rules、回退原因、账本请求引用及最终报告 hash。复用现有脱敏、检查点和证据存储，不额外复制整套采集历史。

新的 response、最终建议和 report 记录在同一节点更新中进入检查点，在既有 report/draft 事件之前确定；刷新与关闭重开只读已保存结果。旧 checkpoint 缺少 report 时按旧记录读取，不回填、不重写。

已有终态可防止普通刷新和重复读取再次请求；进程在付费请求返回后、检查点提交前崩溃，现有持久化没有外部请求 exactly-once 保证。第一版不承诺付费报告的自动崩溃续做；异常恢复必须先核对已有请求记录，缺少最终报告时使用规则结果，不能直接重放模型请求。这一分支需要专门验证；如果现有恢复入口无法识别这类中断，先补最小尝试记录再开启模型编排。以后若要求跨崩溃自动续做且绝不重复计费，再单独评估更强事务机制，不能悄悄增加队列服务。

## 7. 实施小阶段与可观察验收

1. **先修报告语义底座。** 用本场保存输入和最小配置错误输入构造证据包、对象归并、合法解释/行动与规则报告；不调模型。明确复现当前四对象并列和三份泛化建议的问题，修后主处理对象与条件复测顺序清楚。两个独立故障及证据冲突的反例不能被错误压成一个。
2. **接入受限模型编排及失败回退。** 使用假模型覆盖合法编排、错对象、错引用、漏独立故障、越级因果、删未知、非法 JSON、拒答、超时、预算拒绝。验证不发生格式二次请求，主/备实际请求都经账本，既有调查重试不被改变。
3. **完成现有读取链路。** 直接相关的策略、建议、结构化输出、评测消费及 SSE/关闭重开读取回归；检查主报告与 diagnosis 建议同源，旧 checkpoint 正常读取且零补调用。前端不修改；如发现现有展示必须调整，先说明具体必要性再纳入。
4. **交付离线修前/修后对照。** 原输入和原结果 hash 不变，新投影写到独立目录；分别报告规则改善、模型路径覆盖、费用/刷新验证及未验证项。离线完成不等于真实模型效果提高。

通过以上门槛后，如要测试真实编排，另行确认本阶段的一次最小真实调用范围和预算。优先用同一已保存且有效的证据包检验报告，无需先重新注入故障、重新调查或开展四组。完整人工照建议处理并复测属于下一层业务验收，不能用文本对照代替。

## 8. 为什么现在不拆独立服务

当前只有现有诊断后端使用，证据、权限、预算与检查点都在同一进程链路，尚无独立扩缩容或跨团队发布的实际要求。内部模块能完成职责分离；“报告是一项独立职责”不是“必须多部署一个进程”的充分理由。

拆服务会新增：镜像/进程及部署发布、服务鉴权与证据传输、网络超时与重试幂等、预算跨服务一致性、输入输出版本、健康检查和监控告警，以及故障恢复和值守。当前这些工作不能直接改善报告对象归并和证据表达，暂不承担。

只有出现多个独立消费者、报告负载实际影响调查服务，或确有独立权限/发布边界时再评估；届时先用本次模块接口作为迁移边界，不提前搭新基础设施。
