# Windows Probe 隔离故障验收清单

本清单区分本机专用测试应用和隔离 Windows 环境。当前电脑允许对本项目明确创建的回环测试应用及模拟下游验证进程退出、HTTP 错误、依赖不可达和专用端口冲突，只操作可核实归属的测试进程，并在结束后恢复、核对无残留监听。不得停止现有业务或系统服务，不做持续 CPU 压力、系统盘空间耗尽或扩大真实业务白名单。服务停止、整机资源故障等场景仍需隔离 Windows 虚拟机或测试主机。

本机采集脚本为 scripts/verify_windows_local_faults.py；默认由脚本选择场景与检查顺序，验证真实采集和固定模型流程，不是自主根因盲测。增加 --evaluation-preflight 可在正常和下游不可达时调用 evaluate_windows_probe.py 的免费预检，保存并校验现场证据。具体证据及失败历史见 docs/history/windows-local-fault-verification-20261017.md。evaluate_windows_probe.py 默认仅预检，支持 --probe-config、--symptom-file 和不覆盖已有目录的 --output-dir。verify_windows_local_faults.py 已接入显式 --run-model 的两场串行编排及累计5元费用账本，第二场继承第一场请求与预留，费用不明或执行失败时停止并清理；该参数不能代替用户授权。编排与账本边界仅经过离线测试，真实付费路径未运行。最新默认免费现场回归17个检查条目通过、model_calls=0，不能声称真实模型故障盲测通过。真实模型故障验收仍需新费用授权。

## 每个场景的统一流程

2026-10-24新增相同入口503对照：下游进程退出与应用max_attempts解析ValueError，两者响应正文一致，下游探测和真实请求日志不同。仅加入免费控制器预检，真实模型样本列表保持原范围。完整现场27检查条目、48条控制器证据通过，机制36条另计；详细边界和产物见[相同503故障验收](matching-503-faults-20261024.md)。

1. Probe 已连接，目标状态为 `online`，最近 baseline 未过期。
2. 只把用户侧症状交给 AIOps，不提供故障类型或答案。
3. 保存完整事件流、证据时间线和最终报告。
4. 核对每条结论是否包含真实 `target_id`、`collected_at`、`source` 和原始证据 hash。
5. 核对 Agent 是否检查了关键替代解释；没有证据时必须报告“未定位/证据不足”。
6. 确认没有调用 Probe 写操作、任意 Shell、服务重启或配置修改工具。

## 场景矩阵

| 场景 | 隔离环境动作 | 期望优先证据 | 不能接受的结论 |
|---|---|---|---|
| 服务停止 | 停止白名单 Windows Service | `probe_service_status` 显示 stopped，相关 Event Log | 只凭用户描述断言应用崩溃 |
| 进程退出 | 结束白名单进程，保持 Service 状态可见 | `probe_process_snapshot`、服务与进程对照 | 把 Service running 当作进程健康 |
| 端口冲突 | 由无关进程占用配置端口 | `probe_port_snapshot` 的 PID/进程名 | 没有端口证据就断定绑定失败 |
| 数据库不可达 | 仅阻断配置中的数据库地址或端口 | `probe_dependency_probe` 的 DNS/TCP/HTTP 结果 | 把网络探测失败直接当成数据库内部故障 |
| 应用日志报错 | 写入测试应用白名单日志的错误事件 | `probe_text_log` 或 `probe_event_log` | 把知识库示例当作现场证据 |
| CPU 持续升高 | 在隔离应用进程中制造可回收 CPU 负载 | resources/processes 前后 baseline | 只看到瞬时 CPU 就下结论 |
| 磁盘空间不足 | 使用隔离盘或可删除测试文件降低空间 | resources 磁盘 free/percent，时间对齐 | 对系统盘做不可逆删除 |
| HTTP 健康检查失败 | 让配置依赖的测试健康接口返回失败 | dependency probe 的 status/body_prefix | 使用未配置的新地址探测 |

## 通过条件

单个场景只有同时满足以下条件才算通过：

- Agent 选择了与症状相关的 Probe 数据源，并能根据新证据换方向；
- 故障对象或故障层由现场原始证据支持；尚未知的原因明确保留，不把连接失败直接解释为进程崩溃。当前调查无自由文本因果验证能力，不以自动确认根因为必达门槛；
- 关键替代解释已检查，或报告明确说明无法检查；
- 证据时间、目标和来源可在 AIOps 证据时间线复核；
- 证据过期、目标不匹配或 Probe 离线时没有被当作当前事实；
- 没有执行未审批的修改、重启或任意命令。

正常场景和每种故障场景都要分别记录。真实模型结果与确定性流程测试分开报告，不能用规则测试结果代替未知答案调查。

2026-10-24评分口径补充：机械门槛、流程完成、结果等级与人工语义意见分别记录；修复建议的引用/结构参与机械检查，适用性另由人审核。使用新的离线审核包绑定源hash，不填意见就保持pending。详见[评分与人工审核核验](diagnostic-review-20261024.md)。本页早期资源故障矩阵仅为历史范围，当前本科必达范围仍是独立测试应用的应用级故障，不据此扩大为整机资源故障。

## 2026-10-23 控制器核对与真实免费复验

发现并修复：模型编排原先只切换场景，未独立确认故障；恢复也只记成功标签。现 set_model_case 每次通过 verify_case_state 核对入口/下游 HTTP、进程退出、监听 PID 属于本轮进程或子进程，端口冲突还核对绑定失败。失败快照写 controller-observations.jsonl 并阻断后续模型启动。恢复失败保存 recovery=failed 与异常类型，同时保留原调查失败。控制器检查不冒充 Agent 证据，不传入模型上下文或 Probe 工具白名单。

真实子进程测试发现：入口客户端和应用内部下游请求同为 2 秒超时，断开下游时客户端可能先超时而收不到应用实际返回的 503。现内部下游请求使用 0.5 秒超时，入口核对保持 2 秒。另删除 missing_evidence 的日志删除动作：请求会立即重建日志，不能将该动作解释为日志不可得；该场仍由既有 --limited-evidence 固定限制调查工具，不以删除成功证明缺证据条件。

### 场景与机制的实际关系

| 场景 | 可独立核实的现场状态 | 机制验收边界 |
| --- | --- | --- |
| normal | 入口和下游均 200，监听属于本轮存活进程 | 正常/误报对照，不要求触发机制 |
| downstream_unreachable | 入口存活返回 503，下游进程退出且无监听 | 可作为保护开发场景；仅模型确实提出又遗漏或无依据排除候选时才有保护机会；TCP 失败只支持连通层 |
| application_error | 入口存活返回 500，下游独立 200 | 可反驳“下游 TCP 失败”的预期；模型若第一次就判断正确，记录未触发。与 503 症状不同，尚不能宣称已构成严格相似症状对照 |
| application_exit | 本轮入口进程退出、无监听，下游 200 | 退出对照；python.exe 名称会匹配其他 Python 进程，不能用列表非空证明入口存活 |
| port_conflict | 本轮应用绑定失败，另一受控进程占用端口并可能返回 200 | HTTP 正常不能证明正确应用存活；当前进程名口径尚不足以稳定证明 owner mismatch，不能预报机制成功 |
| missing_evidence | 与应用错误相同的业务状态，调查工具固定收窄 | 证据缺失/诚实未定位对照；控制器健康检查本身不能证明调查工具确实不可用，仍需工具轨迹核验 |

所有场景使用相同中性请求、配置对象和原始采集，控制器不预写模型候选；机制不触发、保护错误方向的代价和失败都保留。当前尚无新机制真实模型结果，不能把这些开发场景当作保留测试样本或提升证据。

## 2026-10-23 四组运行入口与配置审计

evaluate_windows_probe.py 新增可选 --mechanism-group：G00 全关、G10 仅保护、G01 仅矛盾触发、G11 全开。四组仍进入同一自主调查实现；保护期限、知识与工具条件不因组别改变。单个子进程只运行一组，沿用独立输出目录、数据库、checkpoint 和随机 thread；不是在共享状态中依次翻转开关。无组别时兼容原设置，不将其结果默认视为某一实验组。

免费入口示例（需已有授权的本机 Probe 配置；下列仅说明命令，不代表已执行）：

```powershell
& ./.venv/Scripts/python.exe scripts/evaluate_windows_probe.py --probe-config <配置路径> --mechanism-group G00 --output-dir <新的独立目录>
```

没有 --run-model 时仍为免费预检。mechanism-preflight.json 只保存请求组别与配置，runtime_verified=false，不能当成实际调查组别已验证。真实调查需另行获得费用授权后才加 --run-model；控制器 verify_windows_local_faults.py 的 --run-model 路径也支持 --mechanism-group，继续沿用 --previous-cost 累计账本。机制组禁止搭配 --knowledge-disabled 或 knowledge-control 阶段；缺证据场景可作为固定条件，但四组必须相同。

运行后保存 mechanism_trace.json：实际 thread、每次重规划后的步数、下一计划、候选状态和事件、最终实际执行步骤，以及审计结果。读取现有 checkpoint，不从组别标签伪造事件。审计核对初始配置、逐轮跟踪配置、最终诊断配置及跟踪一致性；关闭机制仍出现对应事件也失败。指定组别但缺轨迹或配置不符时，summary.json 与费用账本保留，子进程失败退出；控制器拒绝错误组别、伪成功或实际配置不符结果。未指定组别的旧用法仍记录审计状态，保留兼容。
