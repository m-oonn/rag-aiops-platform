## 关键发现

1. **真实模型会调查，而不是只复述症状。** 正常场景实际检查了入口、监听端口、进程、日志和依赖；故障场景实际追查了入口与下游，并保留了目标、时间、hash 和 `ev-*` 引用。
2. **模型遵守了“不确定就不猜”。** 正常场景因 Probe 服务查询返回 unavailable、历史基线与当前现场矛盾，没有宣布整机健康；下游场景只确认连接拒绝和应用 503，没有断言“数据库崩溃”或“进程因何退出”。
3. **自主调查仍未达到目标门槛。** 正常应至少输出 `healthy_within_scope`，下游不可达应至少输出 `localized_fault`；两场都降级为 `unlocated`。这说明当前证据门槛、测试对象目录和模型调查提示之间仍有可用性问题，不能把“完成了工具调用”当成根因定位成功。
4. **本轮没有验证知识库效果。** 知识 MCP 被装配进工具面，但两场模型实际调用次数为 `0`；因此不能声称知识库帮助了调查，也不能比较启用/禁用知识的差异。知识对照必须另行授权并使用两场匹配条件。
5. **机械复核器已修正。** 原复核器只在工具轨迹的传输序列化文本中匹配引用；模型引用来自脱敏证据文件，嵌套 JSON 的转义差异会造成 `quotes_observed=false`。现已改为按 `evidence_id` 从本场 `runs.sqlite` 读取 `aiops_evidence.raw_ref` 的完整脱敏证据，再做引用匹配；没有证据账本的旧测试夹具仍回退到工具轨迹。修正后两场的结构、目标、引用、工具和现场观测机械门均通过，但因果正确性仍需人工裁决。
